# Changelog

Each section names the release its changes ship in; dates are on [GitHub releases](https://github.com/Vanclief/compose/releases), which also document the earlier versions.

## v1.20.1

### Highlights

- **`compose` CLI**: `go install github.com/vanclief/compose/cmd/compose@latest` installs a `compose` binary whose `reference` subcommand renders the API reference page of an OpenAPI spec (YAML or JSON) given with `-head`. `-base` names an older spec and turns on diff mode, with the "What changed" section and change badges; `-title` and `-server` set the page title and the base URL of curl samples and the try-it client. `-out page.html` writes a self-contained page with its CSS and JavaScript inlined, stdout gets it when neither `-out` nor `-serve` is given, and `-serve 127.0.0.1:8090` serves it from a local server that re-reads and re-renders both specs on every `GET /`, answering a read or render failure with 500 and the error as text and any other request with 404. Errors name the spec file that failed, and a wildcard address such as `:8090` is reported as `http://localhost:8090`. Exit codes are 0 on success, 1 on a runtime error and 2 on a usage error.
- **Dependencies**: echo v4.16.2, closing the four Dependabot alerts on 4.15.4: GHSA-cxf3-9h37-7rr8 (critical, Proxy forwarded requests after a rejected WebSocket upgrade past the router), GHSA-9969-6676-49h5 (Proxy kept connections after a WebSocket client left), GHSA-h7wr-284f-5qvc (Decompress had no limit on the expanded body) and GHSA-f48p-c9v4-h7xv (BodyDump captured bodies without a limit). Compose uses none of those middlewares, so no consumer was exposed through it. Also golang.org/x/net v0.62.0 (GO-2026-6866 and GO-2026-6860, in packages compose does not call) with x/crypto, x/sync, x/sys and x/text moved along.

## v1.20.0

### Highlights

- **Promoted MCP tools**: `mcp.Config.Tools` names catalog functions (operations or composites) that the server also exposes as first-class tools next to the fixed set, for clients that should call them without `search_functions` and `describe_function` first. A tool is named after its function with the dot replaced by a hyphen, `units.list` as `units-list`, because claude.ai rejects the whole tool list when one name breaks `^[a-zA-Z0-9_-]{1,64}$` and the LLM APIs allow the same characters. The description is the summary, description and return type `describe_function` shows. The input schema holds the JSON Schema of each argument with refs resolved, including its enum, default and the number, string and array bounds; required and path arguments are required and no other properties are allowed. `ReadOnlyHint` and `IdempotentHint` follow `ReadOnly`, and `DestructiveHint` is set only for `DELETE` operations, since MCP reads false as additive-only. A call behaves exactly as `call_function`: the REST response as text, errors as one line, and the function description appended on invalid arguments. `New` refuses with `ez.EINVALID` an unknown or duplicate name, a tool name that breaks that rule, an argument name outside the Claude API's `^[a-zA-Z0-9_.-]{1,64}$` for property names, and an input schema of more than 1000 nodes, a budget that bounds the inline expansion of shared references. The instructions list the promoted functions with their tool names. Promoted tools appear in `Snapshot` under `tools` with their schema, so a host's golden changes when the list changes; a server without `Tools` gets no new `tools` entries.
- **In-process calls**: `mcp.Server.Call(ctx, header, name, args)` invokes a catalog function with the REST headers given, as `call_function` would, without the MCP transport, and `mcp.Function.InputSchema` returns the JSON Schema a promoted tool advertises. A host that embeds its own agent builds a tool list from `Catalog().Functions()` and the same schemas, filters by `ReadOnly` or `Destructive` itself, and calls through `Call`. `mcp.Function.ToolName` gives the hyphenated name a promoted tool uses, so a host's own tool list matches the MCP one. It only swaps the dot: `New` checks promoted names against `^[a-zA-Z0-9_-]{1,64}$`, and a host listing other functions should check them too.
- **Nullable component arguments**: a query, header or body argument `{$ref, nullable: true}` or `anyOf: [{$ref}, {type: null}]` is now typed `Address?` in `describe_function` and in `Snapshot`, and its schema admits null. A path argument is never nullable, since dispatch refuses null for it, so one declared nullable inline is now typed `integer` instead of `integer?`. In a tool schema, null from `nullable` or a `null` in the type list joins the types and leaves the enum and const deciding, as OpenAPI 3.0.3 and JSON Schema say, while null from an explicit `{type: null}` member of `anyOf` or `oneOf` is valid whatever they say; the new `reference.Schema.NullMember` records which form the document used. A host whose API has such arguments sees its golden change by those types.
- **Bodies with rules over their properties**: a request body whose root has `minProperties`, `maxProperties` or `not` is now one `body` argument in `describe_function`, `call_function` and promoted tools, as bodies with `oneOf` or `anyOf` already were, so the rule reaches the tool schema; a host whose API has such bodies sees its golden change.
- **OAuth deny**: `oauth.Server.Deny(ctx, requestID)` ends a pending authorization request with `access_denied` and returns the redirect URL carrying the client's state, for consent pages served from `LoginURL`. Single use, like `Approve`; an unknown or used request is `ez.ENOTFOUND`.
- **Loopback redirect URIs match without the port**: per RFC 8252 §7.3, `authorize` accepts an `http` redirect URI on `localhost`, `127.0.0.1` or `::1` whose registered form differs only in the port, so Claude Code's `http://localhost/callback` works with its ephemeral port. `https` URIs and other hosts still match exactly, and a `redirect_uri` sent to the token endpoint must be the one used at authorize, port included. The OAuth example in [docs/auth.md](docs/auth.md) now sets `AllowedRedirectHosts` to `claude.ai`, `claude.com`, `chatgpt.com`, `localhost` and `127.0.0.1`.

## v1.19.0

### Highlights

- **`components/auth/oidc`**: verifies Google, Apple and Microsoft ID tokens. `Verifier.Verify` checks the RS256 signature, issuer (Google without the scheme, Microsoft multi-tenant issuers against `tid`), audience against the provider's `ClientIDs`, expiry and nonce (the raw value or its SHA-256 hex, required unless `AllowMissingNonce`), and returns an `Identity` normalized across providers (`Subject`, `Email`, `EmailVerified`, Apple's string-or-boolean claims and `PrivateEmail`, Google's `hd` as `HostedDomain`, Microsoft emails never verified). Discovery is lazy and cached; the key set is refreshed in the background after 24 hours and on an unknown `kid` (at most once a minute), serving cached keys through an outage for up to 7 days (`Config.OnFetchError` reports the failures the cache covers); a provider that does not answer is `ez.EUNAVAILABLE` and one that answers an unusable document `ez.EINTERNAL`, never `ez.ENOTAUTHENTICATED`. Discovery and signing keys are fetched and cached by the package itself, so Microsoft's per-key `issuer` restriction is enforced, and the token is verified with `github.com/go-jose/go-jose/v4` (new direct dependency).

## v1.18.0

### Breaking

Bearer-token authentication replaces the `API-KEY` and `API-SECRET` headers. See [docs/auth.md](docs/auth.md) for the migration steps.

- `StandardRequest.Authenticate` reads `Authorization: Bearer <token>` and the `WithCookie` cookie, nothing else, and `AuthenticatedRequest` is `{Token, FromCookie}`: `APIKey` and `APISecret` are gone. The legacy `API-KEY` and `API-SECRET` pair is read by the separate `StandardRequest.LegacyCredentials(keyHeader, secretHeader)`, which applications compose after `Authenticate` on `ez.ENOTAUTHENTICATED` during their migration and delete afterwards.
- A request with no credentials is `ez.ENOTAUTHENTICATED` (401), not `ez.EINVALID` (400). A malformed `Authorization` header is `ez.EINVALID` and never falls back to the cookie.
- Cookie authentication (`requests.WithCookie`) needs `requests.WithMethod` on `requests.New`. Without it every method is treated as unsafe and needs an allowed `Origin`.
- `mcp.Config.Auth` defaults to `mcp.BearerPassthrough()` instead of `mcp.BearerToHeaders("API-KEY", "API-SECRET")`. Set it explicitly to keep the old mapping. The MCP server parses the header more strictly: a malformed `Authorization` header counts as no token.
- `oauth.Config.TokenPrefix` is required, 2 to 10 characters from `[a-z0-9]`.
- `oauth.Grant.Headers` is removed. `Grant` is `{Subject, Scope}`. `Scope` is stored exactly as the application set it, empty included; the client-requested scope is never granted and only echoes in the token response. `oauth.Pending.Scope` exposes the requested scope to `LoginURL` pages. A grant without `Subject` fails the login with `ez.EINTERNAL`.
- `oauth.Config.Fallback` is now `func(ctx context.Context, token string) (bool, error)`: `true` accepts the token, `false` rejects it with 401, and an error is reported to `OnError` and answered 500 instead of being taken for a bad credential.
- `oauth.Server.AuthFunc` returns the passthrough `Authorization: Bearer <token>` header instead of stored REST headers. The REST API resolves access tokens with the new `oauth.Server.Verify`.
- OAuth tokens are `<prefix>at_` and `<prefix>rt_` and are stored as SHA-256 hashes. Existing token rows are unreadable, so connected MCP clients reconnect once. There is no migration.
- Reusing a rotated OAuth refresh token, or presenting the same refresh token twice concurrently, revokes its token family. A client whose rotation committed but whose response was lost retries with a rotated token and must re-authorize; a failure before the commit is retried with the same token.
- `oauth.Store` gains `Swap(ctx, kind, id, old, value, expiresAt)`, a conditional replace that fails with `ez.ENOTFOUND` unless the stored value equals `old`. Custom stores must implement it; the bun and memory stores do, with no schema change. The Store must give read-your-writes across instances.
- `oauth.New` rejects negative durations and a negative `MaxLoginAttempts`, which used to take the default. The new `oauth.Never` is accepted only by `RefreshTokenTTL`; `IdleTTL` rejects it.

### Highlights

- **`components/auth/token`**: prefixed opaque bearer tokens (`<prefix>_` plus 43 base62 characters, 256 bits), stored as SHA-256 hashes, with `Generate`, `Hash`, `Prefix`, `Check`, `Hint` and `Equal`.
- **`components/auth/session`**: rotating session tokens for first-party apps, by cookie or `Authorization` header. Idle and max expiry, `Manager.Sweep` to delete expired sessions on a ticker (`Store.DeleteExpired`, with `expires_at` and `last_used_at` indexes from `CreateTable`), rotation with a grace period that waits for the previous token's grace to end, reuse detection (the previous token presented after its grace deletes the session, so a rotation response lost on the wire costs a login and a stolen previous token cannot take the session over), `LastUsedAt` writes coalesced by `TouchEvery` (which must be shorter than a finite `IdleTTL`), an optimistic lock on a `revision` column so concurrent requests re-read and re-decide instead of overwriting each other, with `Store.DeleteRevision` making the expiry and reuse deletes one conditional statement, a cookie `MaxAge` that follows `MaxTTL` so sessions without rotation stay logged in, a bun store for PostgreSQL and SQLite, and a memory store.
- **CORS for session tokens**: `rest.Start` sends `Access-Control-Expose-Headers: Session-Token` so browser apps on another origin can read rotated session tokens. `rest.WithCredentialedCORS()` enables `Access-Control-Allow-Credentials` for cookie sessions cross-origin; it only applies together with `rest.WithAllowedOrigins`.
- **Dependencies**: wazero v1.12.0. The project moved to github.com/wazero/wazero; the module path is unchanged.
- **Generator http schemes**: `SecurityScheme{Type: "http", Scheme: "bearer", BearerFormat: "opaque"}` documents bearer authentication in the OpenAPI spec. The global `security` requirement groups all `apiKey` schemes into one requirement object and gives each `http` scheme its own, so bearer is an alternative to the API key pair instead of being required alongside it. Output for apiKey-only configs is unchanged.
- **Configurable OAuth lifetimes**: `RequestTTL`, `CodeTTL`, `RegisteredClientTTL`, `MetadataCacheTTL`, `RefreshTimeout`, `IdleTTL` and `MaxLoginAttempts` join `AccessTokenTTL` and `RefreshTokenTTL`, and `RefreshTokenTTL` accepts `oauth.Never`, which makes the connection end `IdleTTL` after its last refresh instead of at a fixed time.
- **OAuth refresh rotation on one conditional write**: the family row is the single source of truth, holding the grant, client, expiry and the generation of the current refresh token; access and refresh rows only point at it. A rotation writes the new rows, then commits with one `Store.Swap` of the family row, the last write before the response, so any failure before it leaves the presented token usable for a retry. A rotated token presented again revokes the family with one delete, and every token of the family is refused on its next use; a failed revocation answers a retryable `server_error`. Reuse reports name the family and client. Nothing is derived from the configuration after a family is issued, so TTL changes and restarts cannot shorten a revocation. A rotated refresh row keeps the expiry it was issued with and is detected as reuse until then; under `RefreshTokenTTL` `Never` every rotation moves the family to `IdleTTL` from then, so no row outlives the connection and `Sweep` removes them all. Dynamically registered clients are renewed on every code and refresh exchange, before the token rows are written and best effort, not only on authorize, so a client that keeps refreshing never hits `RegisteredClientTTL`.
