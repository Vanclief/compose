# Changelog

Each section names the release its changes ship in; dates are on [GitHub releases](https://github.com/Vanclief/compose/releases), which also document the earlier versions.

## v1.38.0

### Breaking

- **`reference.Diff` reports changes it missed, so a CI gate on `Report.Breaking()` or `Change.Breaking` can fail on a pair of documents it passed.** On the full history of two production specs, 205 revision pairs, no report changed. The new reports, with the `Change.Detail` texts to match on:
  - **A type narrowed by a later `allOf` member or beside a `$ref`**, which compared as the first type stated: `{$ref: Amount}` with `Amount` a number to `{allOf: [{$ref: Amount}, {type: integer}]}`, `{type: number}` to `{allOf: [{type: number}, {type: integer}]}`, and `{type: number}` to `{$ref: C0, type: number}` with `C0` an integer now read `type changed from number to integer`, breaking both, as a type change does. The types of an `allOf` are those every member allows, an integer counting as a number; members whose types share none still compare as the first, as no value is accepted either way.
  - **A property two `allOf` members define, items two members give, and two schemas of additional properties**, which compared as the later property definition, the first items and the first `additionalProperties`: a `maxLength` lowered in the earlier definition of a property, or in the second member's `items` or `additionalProperties`, now reads `maxLength lowered from 50 to 30` under the property, `M[]` or `M › <key>`, and `additionalProperties: false` in a second member, beside a schema in the first, reads `additional properties no longer allowed`.
  - **A discriminator**, which was not compared: `discriminator added: kind` breaks a request, `discriminator removed (was kind)` a response, and `discriminator property changed from kind to type` both. Of its mapping, compared as written by the component each value names, so `Cat` and `#/components/schemas/Cat` are the same, `discriminator mapping added: "cat" → Cat` breaks neither, as enum values added do not, `discriminator mapping removed: "cat" → Cat` breaks a request, and `discriminator mapping "dog" changed from Dog to Wolf` both. The values the mapping leaves implicit, the names of the variants, are not compared.
  - **A parameter's `style` or `explode`**, which were not compared, with the default of the parameter's location where unset, so writing the default out is no change: `style changed from form to pipeDelimited` and `explode changed from true to false` break a request, except a change of `explode` where both sides state a type that is neither an array nor an object, which is written the same either way. `style: form` replaced by `style: pipeDelimited`, with `explode` unset on both sides, reports both, as `form` explodes by default and `pipeDelimited` does not.
  - **`const: null` given, dropped or replaced**, which read as no `const` at all: `const added: null` breaks a request, `const removed (was null)` a response, and `const changed from null to 1`, or the reverse, both, as for any other `const`, also where an `allOf` member or the keywords beside a `$ref` give it.
- **`reference.Parse` refuses a NaN bound.** A YAML document can write `.nan` as the value of `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum` or `multipleOf`. No number compares with NaN, so where an `allOf` member held one, `Flatten` kept it as the tightest bound and the other member's real bound was neither shown, nor used in the example, nor compared by the diff, which said "No changes." when it moved. `Parse` now fails with `ez.EINVALID`, `invalid OpenAPI document: line 11: minimum must be a number, not .nan`. An infinite bound, `.inf` or `-.inf`, is still accepted: it compares with every number, so `Flatten` keeps the right one, the diff reads `minimum: -.inf` and `maximum: .inf` as no bound, and examples stay finite. JSON has neither.
- **`Document.Flatten` merges what several `allOf` members define.** The flattened type is the types every member allows, so `allOf: [{type: number}, {type: integer}]` flattens to `integer` where it was `number`. A property defined in two members, `items` given by two and two `additionalProperties` schemas are each merged into an `allOf` of the definitions, which flattens by the same rules, the tightest bounds of both holding: the later definition of a property first, so where a keyword takes one value it is the later one's, as before, and the first `items` or `additionalProperties` schema first, also as before. `additionalProperties: false` now wins over a schema in another member, and a schema over `true`. A caller that reads `Properties.Map[name]` of a flattened schema without flattening it again, for a property two members define differently, now gets that `allOf`; definitions written the same, and a bare `$ref` beside a definition that refers to the same model, are not merged. The reference page, the generated examples and the input schemas of MCP tools show the merged schema.
- **Generated examples meet `minItems`, `maxItems`, `uniqueItems`, `multipleOf` and `const: null`.** The examples of the reference page and `Document.ExampleValue` held at most three items whatever `minItems` said, copied one item however many there were, also under `uniqueItems`, and ignored `multipleOf`, so an example could fail the schema it illustrates. An array now holds `minItems` items, up to 1,024, and at most `maxItems`, so `maxItems: 0` gives `[]`. With `uniqueItems` its items differ where the item schema lets them: the other `enum` values, the next numbers the bounds and `multipleOf` allow, a string with a number at its end within `maxLength`, `false` after `true`, and an object with one property varied so; where fewer distinct items exist, as for a `const`, a formatted string or two `enum` values, the array holds as many as are distinct. A number or integer is the smallest multiple of `multipleOf` its lower bound allows, `multipleOf` read as the decimal written, so `{type: number, multipleOf: 0.1, exclusiveMinimum: 0.3}` gives `0.4` where it gave `1.3`; where no multiple meets the bounds the example is made as before. A `const: null` gives `null`. `pattern` is still not met.

### Highlights

- **`Schema.ConstNull` tells `const: null` from no `const`.** `Parse` sets it, in JSON and YAML, where `Const` stays `nil` as for no `const`. `Flatten` keeps a member's `const: null` as any other `const`, and beside a `$ref` it is a keyword that applies with the model. A document built without `Parse` sets it itself.

## v1.37.0

### Breaking

- **A malformed config file is no longer reported as missing**: `configurator.LoadConfiguration` reported every error reading the config file as `Config file with path … not found` with `ez.ENOTFOUND`, a JSON syntax error included. A file that is not found keeps that error. A file that is found but fails to parse, as malformed JSON or a JSON array does, is now `ez.EINVALID`, `Config file <path> is not a valid JSON object`, with the parse error as cause, and any other read error, such as a file the process may not read, is `ez.EINTERNAL`, `Config file <path> could not be read`. A caller that matched `ez.ENOTFOUND` to catch a malformed file now gets `ez.EINVALID`.
- **MCP: enum values are written as JSON, and an alternative with an enum is parenthesized.** The type notation of `describe_function`, `explain_term`, `search_functions` results, the argument list after an invalid-argument error, the `Returns` line of promoted tools, the reference page and `Server.Snapshot` joined both enum values and `oneOf`/`anyOf` alternatives with `|`, so a filter read `string enum: valid|invalid|string[] enum: valid|invalid`, and an allowed empty string showed only as a bar, `enum: a|`. Enum values are now JSON values, strings quoted and escaped as JSON strings, with `<`, `>` and `&` left as they are, numbers and booleans bare and null as `null`: `enum: "valid"|"invalid"`, `enum: "a"|""`. In a list of alternatives, a member that has an enum is wrapped in parentheses: `(string enum: "valid"|"invalid")|(string[] enum: "valid"|"invalid")`; members without one are not. A list of two or more alternatives that is nullable or is the items of an array is wrapped in parentheses too, before its `?` or `[]`: `((string enum: "a")|integer)?`, `(Unit|string)[]`. A host or test that matches the old text, such as `enum: a|b`, must match the quoted values instead, and a project that commits `Server.Snapshot` regenerates it.
- **MCP: a call whose path argument is empty is refused instead of sent.** A path argument that renders as nothing, such as `""`, `[]`, `[null]` or `[""]`, left its segment empty, so `runs.get_run {"id": ""}` requested `GET /runs/` and the agent got a misleading `not_found`, or the answer of another route. `call_function`, promoted tools, `run_script`, `Server.Call`, `Server.CallTool` and a composite's `Caller.Call` now fail such a call with `invalid` and the message `<function> requires a non-empty path argument <name>`, after `mcp: ` in the Go error, before the function's request is made; `call_function` and promoted tools follow it with the function's description, as for other invalid arguments, and a script gets it as an Error with `e.code` `invalid`.
- **MCP: a call whose path argument makes a `.` or `..` path segment is refused instead of sent.** A path argument is escaped into the path, and escaping leaves dots as they are, so `runs.get_logs {"id": ".."}` requested `GET /runs/../logs`, which a handler that cleans the path before routing answers as `GET /logs`, the route of another function or of none in the catalog. The same callers now fail a call with `invalid` and the message `<function> path arguments must not make a path segment of . or ..` when a segment of the path, with its arguments filled in, is exactly `.` or `..`; a value such as `...`, `a.b` or `../a`, whose slash is escaped, is sent as before.

### Highlights

- **Instances booting together can all create their tables and extensions**: `relational.DB.CreateTables`, `relational.DB.CreateExtensions`, `oauth.CreateTable` and `session.CreateTable` ran `CREATE TABLE IF NOT EXISTS`, `CREATE EXTENSION IF NOT EXISTS` for `CreateExtensions`, and the last two `CREATE INDEX IF NOT EXISTS`, with no lock, so on PostgreSQL two instances creating a missing table or extension at the same moment could fail one of them with a duplicate key error on PostgreSQL's catalog (SQLSTATE 23505) or with `already exists`, and an app that calls them at boot could crash one instance on the deploy that adds a table. On PostgreSQL `oauth.CreateTable` and `session.CreateTable` now create their table and indexes in one transaction that first takes a transaction-level advisory lock, as `claims.CreateTable` does, with a key of their own that is not the migration lock's. `CreateTables` now runs a model's statement again, up to twenty attempts in all, when it fails on the catalog (a unique violation on a PostgreSQL catalog index, SQLSTATE 23505, or 42P07 or 42710) because another instance created the object at the same moment; a model's create-table hooks run on each attempt, the same error twice in a row ends the attempts, and a failure still leaves the models before the failing one created. A hook statement that rewrites an existing catalog row, such as `CREATE OR REPLACE FUNCTION` or `GRANT`, can still fail when instances run it at the same moment, with an error that is not retried. `CreateExtensions`, and so `relational.WithExtensions`, runs each `CREATE EXTENSION IF NOT EXISTS` again the same way. Every instance can call the four at startup. SQLite is unchanged.
- **MCP: `explain_term` lists the functions that use a term through `oneOf` or `anyOf`.** Its accepted by and returned by lists followed only a direct `$ref` and array items, so a filter declared as `oneOf: [Severity, Severity[]]` left its function out of `explain_term Severity`, though the see also line of `describe_function` named the term. They now follow `oneOf` and `anyOf` members and array items at any depth, for parameters, request bodies, each top-level property of a flattened body, and responses; the properties of an inline object are still not followed. The `accepted_by` and `returned_by` lists of `Server.Snapshot` gain those functions, so a project that commits it regenerates it.
- **MCP: "did you mean" puts the closest names first.** The suggestions of `describe_function` for an unknown name were the first five functions in catalog order containing the name or the part after its dot, so where five functions containing "me" came earlier in the catalog, `Users.Me` got those and not `users.me`. The function whose name equals the given one in another case now comes first. For a name with a dot the functions containing the whole name come next, then those whose part after the module equals, in any case, the given name's part after its first dot, then those containing that part, so for `user.me`, `users.me` comes before the functions that only contain "me". For a name without a dot, such as `me`, the functions whose part after the module equals it come before those that contain it.
- **MCP: a `search_functions` query of only underscores or punctuation matches nothing.** Underscores count as spaces, so a query such as `___` left no words, which every function matched, and a query of `.` matched every function by the dot in its name, so the whole catalog came back. A word without a letter or a digit is now dropped from the query, and a query that leaves no words answers `no functions match "___"` with the module list, with or without a module. Punctuation inside a word is searched for as before, so `get-order` and `packages.register` find what they found; an empty query still lists the modules, or the functions of the module.
- **MCP: an integer of magnitude 2^53 or more, written as an integer, reaches the handler with its digits.** The arguments of `call_function` and of promoted tools were decoded as float64, so `9007199254740993` went out as `9007199254740992` in the path, the query, a header and the JSON body, `100000000000000000000000` went out as `1e+23` in the body, and a composite's `int64` or `uint64` field got the rounded value or failed to decode. A number written without a fraction or an exponent whose magnitude is 2^53 or more now keeps its digits, over the transport and through `Server.CallTool`; every other number is sent as before, so `1.0` still goes out as `1` and `9007199254740993.0` is still rounded. The fixed tools now validate and decode their arguments in compose on the transport too, as `Server.CallTool` already did. Their input schemas are the same, and so are their answers except the wording of two refusals, which now comes from `encoding/json` instead of the SDK's decoder: arguments that are not a JSON object, such as `[]`, `"x"` or `5`, and a number no float64 holds, such as `1e400` or an integer of 400 digits, whose refusal no longer names the argument; over HTTP the SDK refuses such a number itself, before any tool runs, for clients on MCP protocol 2026-07-28 or later. `run_script` keeps the limit: a script's numbers are JavaScript doubles, so it cannot pass every integer above 2^53 exactly.

## v1.36.0

### Highlights

- **Keyed jobs can exclude each other across instances**, opt-in with `scheduler.WithLeaser(l)`. Without it a job id excludes other runs of the id in one process only, as before. With it every run of an id, `RunOnce`, `RunNext`, `Supersede` and recurring runs alike, holds the id's lease in a shared store while it runs, so at most one run of an id is going across the instances. A `RunOnce` or recurring run is skipped while another instance holds the id; `RunNext` and `Supersede` wait for it, for up to their job timeout plus 30 seconds. `Supersede` marks the lease on every attempt until its job gets it or gives up (its context ends, the Scheduler stops, or its bound passes), and the instance holding a marked lease cancels the run on it with `ErrSuperseded` at its next successful renewal, which it attempts every 2 seconds, so every run holding the id meanwhile is cancelled, also one that started after the call, such as the holder's own pending job or the job of another `Supersede`; of two `Supersede` calls on different instances at the same time, one job runs to completion and the other is cancelled, runs after it or gives up at its bound, in no guaranteed order. A mark left by a `Supersede` that gave up stays on the lease while its holder keeps it, so it can still cancel the run then holding the lease at that renewal, with no job replacing it. A run whose lease was taken from it is cancelled with the new `scheduler.ErrLeaseLost`, and so is a run that can no longer renew its lease, 10 seconds before another instance could take the id. The bools those methods return still mean "accepted on this instance". `components/scheduler/claims` implements it on PostgreSQL with `claims.CreateLeaseTable(ctx, db, table)` and `claims.NewBunLeaser(db, table)`, one autocommit statement per operation on the database clock, so it works through PgBouncer in transaction mode. Set it on every instance, on the same table, together with `WithClaimer`; [docs/scheduler.md](docs/scheduler.md) lists what it does not guarantee.

## v1.35.0

### Breaking

- **`query.ParseDateToFilter` is gone; `query.TimeRangeFilters` bounds a column by the two instants as given.** `ParseDateToFilter` added 24 hours minus one second to its upper bound whatever the bound was, so a client that asked for rows up to `2026-03-12T17:45:10Z` got rows up to `2026-03-13T17:45:09Z`. That served one convention, a client that sends the instant its last day starts, and was wrong for every other upper bound. `TimeRangeFilters(column, from, to)` takes the same arguments, refuses the same input with the same messages, and adds nothing: both bounds are in the range, compared in whole seconds. Go code that calls `ParseDateToFilter` no longer compiles, so the change cannot go unnoticed in a list that would otherwise lose its last day. An endpoint whose clients send the start of the last day keeps that contract in the app: when the upper bound is not empty, parse it, add `24*time.Hour - time.Second`, and pass the result formatted as RFC 3339, answering a value that does not parse with the app's own `ez.EINVALID`. Clients that can change send the last second they want.
- **The OpenAPI generator reads route files as Go code, so a route written over several lines is now in the spec**: the route finder of `components/rest/generator` read route files one line at a time and only skipped `//` comments. A route call inside a `/* ... */` block or a raw string literal was documented as a real route, and a call spread over several lines, such as `e.POST("/units/:id",` with the handler on the next line, was silently left out. Each route file is now parsed with `go/parser`, and routes and groups come from the code itself: comments and string literals declare nothing, and a call written over several lines is one route, reported at the line where the call starts. An app sees the routes it wrote over several lines appear in its spec, and commented-out routes disappear from it. The handler is read from the argument after the path alone. The body of an inline function literal no longer names it, so such a route written on one line is listed among the routes without a handler unless `Config.Skip` covers it, as it already was when written over several lines; and a middleware argument after the handler no longer names it either, where `e.GET("/health", health, h.Auth.Required)` was documented as `Auth.Required`. `Config.DeprecatedWrapper` is matched as a call of that function among the arguments after the path, on any line of the route call, also when it is written with a qualifier (`mw.logDeprecated(...)`; a wrapper configured as `mw.Deprecated` matches only that qualifier), type arguments or parentheses, where it was searched as text on the route's first line: a deprecated route whose wrapper stands on a later line is now marked, and a comment, a string literal or a function whose name only ends with the wrapper's, such as `mylogDeprecated(...)`, no longer marks one. A route call is found wherever it stands in the file, not only at the start of a line, so a call of the same shape on something that is not a route group now fails generation with `unknown route group` when it follows other code on its line, such as `resp, err := client.GET("/x", nil)`, as it already did at the start of one. A route file that is not valid Go now fails generation with `ez.EINVALID` naming the file, where it was scanned as text. The routes of emma-backend and auditor3-api come out unchanged.
- **The OpenAPI generator documents a type with `MarshalText` as a string**: `components/rest/generator` described a type that defines `MarshalText` and not `MarshalJSON` by its kind, so `type Level int` with `MarshalText` was `{"type": "integer", "format": "int64"}` and a struct with `MarshalText` was an object of its fields, while `encoding/json` writes both as the string `MarshalText` returns, such as `"high"` or `"1,2"`. Such a type's component is now `{"type": "string"}`, without the `enum` a closed set of constants gave it. A pointer-receiver `MarshalText` counts too, as `encoding/json` calls it on every field of a response marshaled through a pointer; a value it cannot address, such as a map value, it still writes by kind, which the schema does not describe. A struct into whose method set an embedded type promotes `MarshalText` marshals as that type's text alone, so generation now fails for it with `type X embeds Level, which defines MarshalText`, as it does for a promoted `MarshalJSON`, unless the struct defines its own `MarshalText` or `Config.TypeSchemas` describes it. An anonymous struct has no component and fails generation the same way, with `anonymous struct embeds Level, which defines MarshalText`. Go promotes a method from the shallowest depth of embedding where an embedded type declares it, and only when one path alone reaches such a type there: a struct embedding two types that both define `MarshalText` at that depth, or one such type by two paths, gets neither, is written as its fields and is still described by them. Both checks now follow embedding to any depth, where they looked at the directly embedded types only. A type declared from another named type, `type Priority Level`, inherits none of `Level`'s methods and is written as `Level`'s underlying type, an integer here, so it is described by that type instead of by a reference to `Level`'s component, when `Level`'s own `MarshalText`, or a struct's `MarshalJSON`, makes that component something else, or `Config.TypeSchemas` describes a `Level` that has either method, as the description is of that method's output; the same holds for a type declared from a standard-library or well-known type whose method makes it differ from its kind, so `type Stamp time.Time` is an object without properties, as Go writes `{}` for its unexported fields, where it was a date-time string, `type Severity slog.Level` an integer, `type Addr net.IP` a base64 string, nullable as a field, and `type ID uuid.UUID` an array of 16 numbers; `type Area Point`, with `Point` a struct with `MarshalJSON`, is now described by `Point`'s fields where generation failed, and the `,string` option quotes such a type. An alias, `type A = Level`, is `Level` and keeps its methods, also when embedded, and a method declared on the alias is `Level`'s; an embedded alias of a generic instantiation, `type B = Box[int]`, has `Box`'s methods, and an embedded type declared from one, `type D Box[int]`, what `Box`'s embedded fields promote, where both counted as having neither, and a method declared on a receiver with several type parameters, `func (p Pair[K, V]) MarshalJSON()`, now counts, where it was not seen when `Config.TypeSchemas` described `Pair`; a chain of up to 8 aliases is followed, and a longer one, or a cycle, fails generation. The generator does not substitute type arguments into a generic type's fields, so a type declared from an instantiation of a generic type with `MarshalJSON` or `MarshalText`, `type D Box[int]`, which Go writes as `Box`'s fields as it does not get the method, now fails generation with a reason asking to describe `D` in `Config.TypeSchemas`, where it was a reference to `Box`'s description. A type with `MarshalJSON` is unchanged, `MarshalText` or not, and so is a map keyed by such a type. Of the standard library, a field of a type the generator lists with `MarshalText` and without `MarshalJSON`, `netip.Addr`, `netip.AddrPort`, `netip.Prefix`, `big.Float`, `big.Rat` or `slog.LevelVar`, is now `{"type": "string"}` by the same rule, and a `slog.Level` field, whose `MarshalJSON` writes the level's name, is a string too, where each was a reference to an opaque `{"type": "object"}` component; such a field is now required when it is not a pointer and has no `omitempty`, as Go always writes it. A standard-library type the generator does not list is now described from its declaration in GOROOT's source by the rules for a type read from source, where it was an opaque `{"type": "object"}` component: `time.Month`, `time.Weekday`, `os.FileMode`, `http.ConnState`, `reflect.Kind`, `x509.KeyUsage` and `syscall.Errno` are integers, `template.HTML`, `http.Dir` and, through their `MarshalText`, `regexp.Regexp` and `x509.OID` are strings, `net.IPMask`, `net.HardwareAddr` and `sql.RawBytes` base64 strings and `sort.IntSlice` an array, nullable as fields, `json.Token`, `xml.Token`, `crypto.PublicKey`, `driver.Value` and the other interfaces declared as `type Token any` the empty schema, a struct without a marshal method, such as `time.Location` or `net.IPNet`, stays an object whose fields are not described, and one with `MarshalJSON` and no listing is the empty schema; `,string` quotes such a type, a type declared from one follows the same rules, and a value field of one without `omitempty` is now required, as Go always writes it, except an interface with methods, such as `context.Context` or `fmt.Stringer`, which stays optional, while one declared as `type Token any` is required as an `any` field is. A slice whose element is of kind uint8 without `MarshalJSON` or `MarshalText`, such as `[]Level` with `type Level uint8`, a slice of an alias of `byte` or of a standard-library type such as `elf.Class` or `tls.AlertError`, also through a named slice type, a pointer or a map value, is now a base64 string, as `encoding/json` writes it, where it was an array of integers; an element with either method, a pointer receiver included, keeps the slice an array of what the method writes, and a type declared from such an element, which does not get the method, makes it base64 again. An element that is an instantiation of a generic type is not looked into and stays an array. An app whose spec has such a type sees its component change and regenerates its clients.
- **The OpenAPI generator documents `database/sql`'s Null types as the objects Go writes**: a `sql.NullString` field was `{"type": "string", "nullable": true}`, and the other Null types the same way, while those types define no `MarshalJSON`, so `encoding/json` writes the struct: `{"String": "", "Valid": false}`, never `null` or a bare value. `sql.NullBool`, `NullByte`, `NullFloat64`, `NullInt16`, `NullInt32`, `NullInt64`, `NullString` and `NullTime` now each reference a component named like any other type's (`database_sql_NullString` by default) that is an object with the value field (`Bool`, `Byte`, `Float64`, `Int16`, `Int32`, `Int64`, `String` or `Time`) and `Valid`, both required, and a field of such a type without `omitempty` is now required where it was optional. The generic `sql.Null[T]`, which failed generation as an unsupported instantiation, is now the same object inline with the field `V` described as a field of type `T`. Like any struct outside `Config.RequiredPackagePrefix`, such a component loses its required list once a request reaches it.
- **The OpenAPI generator resolves embedded structs the way `encoding/json` does**: it made each embedded struct an `allOf` member beside the struct's own fields, so a struct that re-declares a name of the struct it embeds, ``Outer{Inner; Name int `json:"name"`}`` with a string `name` in `Inner`, required `name` to be both a string and an integer, which nothing satisfies, while Go writes only the outer field; two embedded structs with the same name at the same depth both required it, while Go writes neither; and an embedded `*Inner` required `Inner`'s fields, while Go leaves them out when the pointer is nil. Such a struct's schema is now one object with the properties Go writes, found the way `encoding/json` finds them, at any depth of embedding: the shallowest field of a name wins, a tie at the same depth goes to the only field whose json tag names it and otherwise drops the name (also for two names of one declaration, ``A, B int `json:"ab"` ``, and for the fields of a struct embedded twice at one depth), and the fields of an embedded pointer are not required. A type declared from a struct described in `Config.TypeSchemas`, `type Price Money`, has that struct's fields, read from its source whatever its description says, as the description is of `Money` and not of `Price`: embedded, it was an `allOf` member referencing its own component, whose required fields a nil `*Price` broke. A generic struct is the exception, as the generator does not substitute type arguments into its fields: a type declared from an instantiation, `type D Box[int]`, is `Box`'s description, and an instantiation, an alias of one or a type declared from one, embedded in a struct that is one object, is an `allOf` member referencing that description beside the struct's other properties, as its field names, which the generator reads, do not depend on the type arguments. Such a struct now fails generation, naming the instantiation and why, when that member would not say what Go writes: the instantiation is embedded through a pointer, at any depth; one of its field names, named in the reason, is shared with another field of the struct that the generator reads (the fields of an embedded type it does not read, one described in `Config.TypeSchemas` or a standard-library struct, are not checked against it, as they are not checked against any other); it has `MarshalJSON` or `MarshalText` that a tie leaves unpromoted; or its declaration embeds a type. Where the instantiation was embedded through a pointer or shared a name, the struct was an `allOf` member referencing the description, which a nil pointer or the other field broke; a struct with a tie of marshal methods, such as `struct{ Plain[int]; JA; JB }`, failed generation with `embeds JA, which defines MarshalJSON`, as any such tie did, and is now described with the instantiation as that member unless the instantiation is in the tie. The schema is a single `{"type": "object", "properties": ..., "required": ...}` instead of an `allOf` of the embedded components, so the embedded struct's component is no longer referenced from it, and a `Config.Schemas` hook that changes that component does not change these copied properties. Embedded structs the generator does not read from source (described in `Config.TypeSchemas` without a marshal method, from the standard library or well known, such as `pagination.CursorRequest`) stay `allOf` members: their names are not checked for collisions, and behind an embedded pointer their properties stay required. A standard-library type the generator does not list fails generation wherever it is needed, as a field or embedded, when GOROOT's source cannot be read, with a reason saying where the generator looked and why it could not read it, also when one file of its package cannot be opened, parsed or have its build constraints evaluated, which the reason names, so a spec is the same on every machine or is not written. A struct without a collision, an embedded pointer or an embedded struct that `MarshalJSON` or `MarshalText` writes when it stands alone keeps its `allOf` unchanged. ### Highlights

- **`types.PhoneNumber` no longer refuses short national numbers.** It required 10 to 14 digits after the country code, so numbers from countries with 8 or 9 national digits were refused (Spain, France, the Netherlands, Australia, Singapore, Switzerland, Belgium and the United Arab Emirates among them), and a three-digit country code let a number of up to 17 digits through. A number is now a `+`, a country code and at least 4 more digits, with at most 15 digits in all, which is the E.164 limit. A stored number of 16 or 17 digits no longer scans or decodes. The route registry's `phone` format follows, since it calls `types.ValidatePhoneNumber`.
- **SES: a sender name with punctuation or accents gives a valid From.** A `SenderName` such as `Acme, Inc.` was written unquoted, which mail parsers refuse, and in an email with attachments a name with a letter outside ASCII, such as `José Pérez`, was encoded together with the address. Such a name is now quoted, or encoded per RFC 2047, with and without attachments. A sender that was printable ASCII and already parsed as an address is written exactly as before: `Emma`, `Acme Inc.`, or a name the app encoded itself as an RFC 2047 word.
- **SES: sending an email with attachments no longer rewrites the caller's `Recipients`.** The slice was handed to the MIME writer, which encodes its values in place, so a recipient with a letter outside ASCII was replaced by its encoded form in the caller's slice and in the recording client's `Outbox`. The To header is now built from a copy. A recipient made only of printable ASCII and tabs is written to it as before. Any other that reads as a single address with a display name and a printable ASCII address, such as `José Pérez <jose@example.com>`, is written as that name and address with the name alone quoted or encoded, where the whole value was encoded before, address included; a comment or a group label on such a recipient is not kept. The rest are encoded whole, as before.
- **`logger.NewZero(...).With` no longer panics on a nil pointer.** `With` calls a method of the value it is given, `String`, `Error` or `MarshalZerologObject`, and a method called through a nil pointer can panic: one with a value receiver always does, as for `(*uuid.UUID)(nil)` or `(*time.Time)(nil)`, and one with a pointer receiver does when it reads its receiver without checking it, as for `(*url.URL)(nil)`. Such a field is now logged as `null`, or left out when the value is an `error`, as a nil error already was. Which method is called has not changed, a method that handles a nil receiver is still called and its result logged, and a panic from a value that is not a nil pointer is not caught.
- **`ratelimit.NewWindowCounter` clamps a window too long for a `time.Duration`.** A window above about 9.2 billion seconds (292 years) overflowed into a negative, zero or shorter window, and with a negative or zero one, about half of such values, the limit was never applied.
- **The API diff reports changed validation rules and response headers.** `reference.Diff`, which feeds the "What changed" section of the reference page and `compose reference -base`, said "No changes." when a request field's `maxLength` was lowered, its `minimum` raised or a `pattern` added, when an object gained `additionalProperties: false`, and when a response header was removed. It now lists a change to `minimum`, `maximum` and their exclusive forms, `multipleOf`, `minLength`, `maxLength`, `pattern`, `minItems`, `maxItems`, `uniqueItems`, `minProperties`, `maxProperties`, `const` and `default`, such as `maxLength lowered from 50 to 10`, and a response header added, removed, made optional or required, or changed in its schema. A header named `Content-Type` is not compared, since OpenAPI ignores it there.
  - **What counts as breaking**: a change that narrows the values a schema accepts breaks a request, since a client sending what used to be valid is now refused, and one that widens them breaks a response. A `pattern`, `multipleOf` or `const` replaced by a different one breaks both, as the diff cannot tell which way it moved. A changed `default` breaks neither. Closing an object with `additionalProperties: false`, or with the false schema written as `{not: {}}`, breaks a request, and so does `items: false` on an array that allowed items; opening it again (`additional properties allowed`) breaks neither, as a new response property does not, except in a model referred to under a `not`, where it counts as widening, while `items allowed` breaks a response. A `not` added narrows and a `not` dropped widens (`not added`, `not removed`). The schemas under two `not`s are compared as written, a `$ref` by the component it names, which is not followed there, and properties, `required` names, types and `enum` values in any order: written the same, they report nothing; different only in annotations, `title`, `description`, `default`, `example`, `examples`, `deprecated`, `readOnly` and `writeOnly`, `not changed` breaks neither; different otherwise, `not changed` breaks both, as the diff does not work out which way a change under a `not` moves, also where a reference under it was only renamed to a model written the same. A `minimum` of `-.inf` or a `maximum` of `.inf`, which restrict nothing, count as no bound, as does a NaN bound. A `not` on an `allOf` member is compared too, the first one found, and a model that either side names under a `not`, also inside variants, and that changed is reported where the outermost `not` stands, or, for a `not` in a variant of a list whose variants changed otherwise, where that list stands, as `not changed: model M changed`, its changes judged strictly and with their flags swapped; under two `not`s it reads `model M changed`, its changes still judged strictly, with their flags as they are. Judged strictly, enum values added, additional properties allowed again and a `format` dropped count as widening the model, and a `format` added as narrowing, though they break nothing elsewhere. `oneOf` and `anyOf` lists of the same keyword and length are still compared variant by variant, so variants that were only reordered are reported as changed where they now stand. Any other change of variants, where a change in their number broke neither, now breaks both, since the diff cannot tell which way it moved, except where the variants as written, with properties, `required` names, types and `enum` values in any order, show it: variants only added widen (`one of variants added`) and only removed narrow (`one of variants removed`); the same variants with one listed more or fewer times break neither (`one of variants changed`); variants given in place of a schema written as one of them, with nothing beside them but annotations and `nullable`, widen, and dropped back to it narrow; variants given beside other keywords narrow and dropped from beside them widen (`any of variants given`, `any of variants dropped`); `anyOf` turned into `oneOf` with the same variants narrows and the reverse widens. A `nullable`, or a `{type: null}` variant, beside the variants is reported on its own, and a 3.1 union of one schema and `{type: null}` is compared as the list of one variant it was written as, under the other side's keyword, where the other side lists variants and that one schema has none of its own, so `{oneOf: [S, I]}` to `{anyOf: [S, {type: null}]}` reads `one of variants removed`, and `anyOf: [S, {type: null}]` to `anyOf: [S, I, {type: null}]` reads `any of variants added`, as the 3.0 spelling with `nullable: true` does; where that one schema is a union itself once flattened, as in `anyOf: [{$ref: U}, {type: null}]` with `U` a `oneOf`, the two sides are compared as they are, as before, so a variant added to that list reads `one of variants changed to any of`, breaking both, though it only widens. A variant added to a `oneOf` is read as widening, as for an `anyOf`, though a value it shares with another variant is then refused, and a variant listed more or fewer times in a `oneOf` breaks nothing, though it changes which values match exactly one. The models that variants kept on both sides refer to count as used there, so their changes reach the operation; a model that only an added or removed variant refers to does not, as that variant is judged by the change of variants. Each keyword is compared on its own, so a keyword another one makes moot is still reported with its own flag, such as `minProperties added: 1` where `required: [name]` was dropped in the same change. A removed response header, or one no longer required, is breaking, and so is a response property no longer required (`made optional`, which broke neither). A property removed from an object that allows no other properties, or whose `additionalProperties` schema limits values and is not written as the property's was, annotations aside and a `$ref` the same where it names the same component, breaks a request as well as a response, since a client may still send it. The two schemas are not compared, so one written otherwise breaks a request even where it accepts every value the property did, while where it is written so and the object was closed before, the models it names are used there, so their changes reach the request, and `patternProperties` is not read for this. A `type`, an `enum` or the schema of array `items` given where there was none narrows by what it refuses, and dropping one widens, except a `type` beside `oneOf` or `anyOf` variants that restate it, each stating that type (an `integer` variant counts as a `number`) and none accepting `null` where the type does not, and `type: object` beside `properties` or an `additionalProperties` that restricts something, or `type: array` beside `items` that restrict something, which the diff infers when no type is stated. A `{type: string}` gaining an `enum` thus breaks a request and not a response (it read `enum values added` and was never breaking; it now reads `enum added: ...`, and an enum dropped reads `enum removed (was ...)`); a change between two stated types breaks both, but for a type of only `null`, read as the type `null` made nullable, which narrows where it is given and widens where it is dropped: `{type: string}` or `{}` to `{type: null}` reads `type changed from string to null`, or `from any to null`, breaking a request, beside `made nullable`. `Parse` marks such a schema with the new `Schema.NullOnly`, as its `Type` stays empty, and so a `oneOf` or `anyOf` of only `{type: null}` beside no type, `$ref` or `allOf`, which reads as `{type: null}` does. Where an `allOf` member gives it, as in `{allOf: [{type: null}]}` or `{allOf: [{$ref: N}]}` with `N` `{type: null}`, it is still read as nullable with no type, so `{type: null}` to that reads `type changed from null to any`, breaking a response, though the two say the same. Beside a `$ref` it is not read as a type either: `{$ref: S}` to `{$ref: S, type: null}`, with `S` `{type: string}`, reads only `made nullable`, which breaks a response only, though nothing is accepted then. Each keyword is compared on its own, so `{enum: [null]}` or `{const: null}` to `{type: null}` reads `type changed from any to null`, breaking a request, though each accepts only null, and `oneOf` or `anyOf` variants given beside `type: null` narrow, breaking a request only. A `type` list written in another order, `[string, integer]` to `[integer, string]`, is no change. On a schema of type `integer`, bounds of magnitude below 2^53 that admit the same integers, such as `minimum: 1` and `exclusiveMinimum: 0`, are not reported, and where the type changes between `integer` and `number` a bound's detail shows the bound the integer side admitted, as in `minimum lowered from 0.5 (1 for integers) to 0.7`. A name in `required` with no property of that name declared is reported as `made required`, breaking in a request.
  - **`no longer nullable` is now breaking in a request**, where it was reported as not breaking: a client that sends `null` is refused. It is not breaking where the schema still accepts `null`: where it states no `type` and no `not`, itself or through a reference or an `allOf` member, with an `enum` only where it lists `null`, a `const` only of `null`, and `oneOf` or `anyOf` variants only where one of each keyword's lets `null` through. A `not` is read as refusing `null` whatever it holds, so `no longer nullable` beside a `not` breaks a request, and `made nullable` there a response, whatever the `not` refuses, and a `oneOf` in which two variants let `null` through is read as letting it through, though the `oneOf` then refuses it.
  - **The schema of additional properties is compared like any other**, with `additionalProperties` absent, `true` and `{}` all standing for the schema that accepts anything. A schema given where the keyword was absent or `true`, or the reverse, was reported as `additional properties changed` and not breaking; it is now reported as what changed under `<key>`, such as `type changed from any to string`, with that change's own flag.
  - **Bounds inside `allOf` are compared as the tightest of the members**, which is what `allOf` means, and keywords written beside a `$ref` are applied together with the model it names. A `nullable` beside a `$ref` in one member of an `allOf` with other members makes the schema nullable only when every member accepts `null`. An `enum`, `pattern`, `multipleOf`, `const`, `not` or `default` is the first one found, so two members with different patterns compare by the first, and so is each of the `oneOf` and `anyOf` lists, so the list of a second member is not compared.
  - **A reference through an alias or a wrapper counts as its model.** A component that only points at another (`X: {$ref: Y}`) and a single-member `allOf` around a reference are compared as the model they name. A property that switched between a model `Y`, an alias of it (`X: {$ref: Y}`) and a component that is a single-member `allOf` around it (`W: {allOf: [{$ref: Y}]}`), or whose component turned from an alias into such a wrapper or back, now reads `model Y changed` when the model changed and nothing otherwise, where what it referred to before still leads to `Y` in the new document. A switch that involved a wrapper component read `schema changed from Y to W`, or `schema changed from W to Y`, an alias named by its model, with the model compared in place; a switch between a model, an alias of it and `allOf: [{$ref: Y}]` written in the property already read `model Y changed`. Where the alias or wrapper switched from is gone from the new document, the model is compared in place and its changes are listed under the property, with no `schema changed` line, also for a switch from an alias, which read `model Y changed`. A `made nullable` that was reported when `{$ref, nullable: true, description}` was rewritten as `{allOf: [$ref, {description}], nullable: true}` is gone, since the keywords beside a `$ref` are no longer dropped. The `description changed` reported with it is gone too where the model has no description of its own; where it has one, `description changed` is now reported instead, as the `allOf` takes the model's description, the first one found.
  - **`Document.Flatten` returns the tightest bound of an `allOf`**, in one keyword: the larger minimum, the smaller maximum, and of `minimum` and `exclusiveMinimum` whichever is tighter. A schema that itself holds both `minimum` and `exclusiveMinimum` is reduced the same way. The reference page, the generated examples and the input schemas of MCP tools, which all read the flattened schema, show that bound for an `allOf` whose members disagree, where they showed the first. A generated number example now respects an upper bound too and is never infinite, an example steps past an excluded bound of magnitude 2^53 and more, and an integer example stays within the range of an int64. For bounds that are exact float64 values, as `Parse` rounds a bound to the nearest one, a number example meets them whenever some float64 does.
  - **The markdown summary escapes text taken from the documents.** `Report.Markdown()` wrote property names and details as they were, so a property named `a*b*c` lost its asterisks when rendered, and a name holding a line break could start a heading. Such text is now escaped, line breaks in it become spaces, it is not turned into a link by renderers that link bare URLs and email addresses, and a `pattern` is written quoted like a `const`. A zero-width space (U+200B) follows every `@`, and every `#` or `GH-` before a digit, so a summary posted to GitHub does not mention an account such as `@github`, link an email address or reference an issue such as `#1`; it reads the same, but a name copied from it holds that invisible character. Model names, written as code spans, get no zero-width space, which is fine because GitHub neither mentions nor links inside code spans. GitHub still links a commit hash it knows and a reference with a custom autolink prefix such as `TICKET-123`, and renders `:+1:` as an emoji.
- **MCP: a call without body arguments sends no body when the operation's body is optional.** `call_function`, promoted tools and `run_script` sent `{}` with a JSON `Content-Type` for every operation that takes body arguments, so an optional body whose schema is an array received an object, and a handler could not tell a call without a body from one with an empty object. A required body with a schema still goes as `{}` when no body argument is passed, so the app's own validation answers; that now includes a required body whose properties are all read-only, for which nothing was sent. A whole-body `body` argument passed as `null` is sent as `null`, where it was `{}`.
- **MCP: operations whose request body is a `+json` media type are in the catalog.** An operation that declared no `application/json` body, only a type such as `application/merge-patch+json` or `application/vnd.api+json`, was left out without a word, unknown to `search_functions` and `call_function`. It is now a function like any other, and its body is sent with the media type the document declares, written in its canonical form: the type in lower case, the parameters kept. A body type of `application/json`, whatever its parameters, is preferred when the operation declares both and is sent as exactly `application/json`, as before. A `+json` key that is not a valid media type, or that holds a `*`, does not count. The handler has to accept the type: Echo's `c.Bind` reads a body only when its type is `application/json` and answers 415 for the rest.
- **MCP: a redirect names where it points.** A handler that answered 3xx with a `Location` came back as `error internal: Found`, which reads as a server fault and hid the location. A redirect that answers the call is now a result, `{"redirect":{"status":302,"location":"/orders/7"}}`: a 301, 302, 303, 307 or 308 on a GET or HEAD, and a 302 or 303 on another method, the two statuses a handler uses to say where the outcome is. A 301, 307 or 308 on another method means the request was not carried out, so it stays an error, and so does any other 3xx, such as a 304; with a `Location` the message now reads `307 Temporary Redirect, Location: /v2/orders`, unless the body is a compose error envelope, whose code and message are kept as before. No redirect is followed, and the body of one that is a result is not read, even when it is an error envelope. The location is quoted without control characters, line and paragraph separators and format characters, and cut at 300 bytes, marked `"truncated":true` in a result and `[truncated]` in an error. A 3xx without a `Location` is the same error as before.
- **Route registry docs: types that decode their own JSON.** `docs/rest-openapi-design.md` now states that an app's request type with its own `UnmarshalJSON` is published and validated by its Go shape, that no value of such a field can be sent when the method reads another form (every request that sends one is a 400, nothing unvalidated reaches the handler), and that giving the type an `UnmarshalText` makes it a string in the document and the validator.

### Highlights

- **`x-destructive` marks a write operation destructive.** A write operation with `x-destructive: true` in the spec, read into the new `reference.Operation.Destructive`, is `mcp.Function.Destructive` like a DELETE, for an operation such as a PUT that sets a policy which deletes data. The MCP catalog then treats it as a DELETE throughout: a promoted tool for it sets `destructiveHint: true` in its annotations, where it was left unset (which an MCP client also reads as true), the reference page gives it the `destructive` badge, and its function in `Server.Snapshot` has `destructive: true`, and a promoted tool for it has `destructiveHint: true` there, so a project's committed snapshot golden changes when it marks an operation. A script that goes on that way without freeing memory gets `null` thrown after a few such errors, which `try/catch` does catch. The 48 MiB limit holds there as before.

### Highlights

- **MCP catalog tools bound their arguments before doing the work**: `search_functions`, `describe_function` and `explain_term` answer from the catalog in-process, past the REST API and its rate limits, and built their whole answer before cutting it to `mcp.Config.MaxOutputBytes`, so any caller with a valid token could make one call cost far more than its request. On the 296-function emma catalog a 4 MiB `describe_function` call naming one function over and over allocated about 560 MiB, one naming 400,000 unknown functions about 3 GiB over 3.6 s, and a `search_functions` query of two million words held a core for 1.7 s. `describe_function` and `explain_term` now take at most 50 names or terms, which their input schemas advertise as `maxItems`, answer a name repeated in one call once (after trimming), and refuse a name or term longer than 256 characters (lengths count characters after trimming); `search_functions` refuses a query longer than 256 characters or of more than 32 words (underscores count as spaces), and a `module` longer than 256 characters. A list that is too long gets the schema refusal an empty one already got, `validating "arguments": ... maxItems: array length N is greater than 50`; the other refusals are one tool error line that does not quote the input back, such as `error invalid: names[1] has 4194304 characters, more than 256` or `error invalid: query has 40 words, more than 32; search for a few words`. Calls within the limits otherwise answer as before, cut with the `[incomplete: ...]` note when long. The arguments are still decoded whole before these checks, so the app's body limit on the MCP route remains what caps a request's size.
- **Validation errors list the failing fields**: when a request to a `components/rest/api` operation fails the registry's request validation, `rest.ErrorHandler` now answers the 400 with a `fields` list next to `code`, `message` and `request_id`, one `{"in", "name", "message"}` entry per failing field in the order `message` joins them: `{"error":{"code":"invalid","message":"query limit must be <= 1000; email is required","request_id":"…","fields":[{"in":"query","name":"limit","message":"must be <= 1000"},{"in":"body","name":"email","message":"is required"}]}}`. `in` is `path`, `query`, `header` or `body`; `name` is the parameter name or the dotted path inside the parameter or the body (`tags.1`, `config.name`, `*` in place of a map key), empty when the entry is about the location itself, such as a missing body; `message` never contains the submitted value. A client can mark the field without parsing `message`.
  - **At most 100 fields**: a request can fail on as many fields as it has values, and the answer to a 1 MiB body of failing array items was about 15 MB of `message`. `validate.NewFieldsError` now keeps the first `validate.MaxFields` (100) fields in its order, so `fields` has at most 100 entries and `message` names the same ones and then ends with `; and <n> more`. That order now compares a run of digits in a name as a number, so the fields kept of a long array are its first items and `steps.2` comes before `steps.10`, where v1.31.0 ordered names as text. A request failing on 100 fields or fewer gets the `message` it got in v1.31.0, but for that order.
  - **Where it appears**: only on an ez `EINVALID` that carries the registry's field errors (`validate.Fields(err)`): a schema violation, a body key that differs from a declared one only by case, a parameter value its Go type refused, a multipart file check. The key is absent on every other error: a failure of the request type's `Validate()`, which is the app's own error (unless the app builds it with `validate.NewFieldsError`), an error of a plain route answered by `handler.ManageError`, and any error with another code. The list is read from anywhere in the error's chain, so an app that wraps the registry's error in its own `EINVALID` answers with its own `message` and the same list. `rest.WithErrorTranslator` still replaces `message` only; the entries keep the registry's English text.

An app type that the registry would also name `handler.FieldError` is refused at boot as a duplicate name. The document of the `components/rest/generator` package is unchanged, because `ManageError` never sets the field. An app with its own `HTTPErrorHandler` builds the same list from `validate.Fields(err)`.

- **Recurring jobs run on one instance per minute boundary**, opt-in with `scheduler.WithClaimer(c)`. Without it every instance of an app runs every recurring job at every boundary, as before. [docs/scheduler.md](docs/scheduler.md)
  - **`scheduler.Claimer`** is the interface: `Claim(ctx, id, tick, lease) (bool, error)` and `Release(ctx, id, tick) error`. At a due boundary the scheduler first skips an id that is busy in the process, as before. Otherwise it admits the run, which makes the id busy, and the run claims the boundary before the job body, so the database round trip is off the minute loop and the job runs only when the claim is won. After a late wake the latest boundary of the caught-up range that the schedule matches is claimed, once. `RunOnce`, `Supersede` and `RunNext` are never claimed.
  - **While the claim is in flight** the id is busy as for a running job: `RunOnce` returns false, `RunNext` and `Supersede` queue behind it, and `Active` counts the id. On an instance that loses, `Active` rises briefly at each due boundary and `Idled` fires when that id was the only busy one. `Supersede` and shutdown cancel the claim's context; a claim that is won anyway is released without running the job, and the PostgreSQL store still answers a claim, won or refused, that was cancelled after it started.
  - **Failures skip the run.** A refused claim (the boundary was already claimed by an instance, this one included after its clock stepped back, or the job is still busy) is logged at debug level. A claim error is logged at error level and skips the run, unless shutdown or `Supersede` cancelled the claim's context: missing a boundary is safer than every instance running it. A claim that errors after its statement committed leaves the job busy, with no run, for the lease.
  - **The claim is released** when the job returns, after a panic or a `Supersede` cancel too, and before a pending job of the id runs; during shutdown, when the job returns and its release finishes within the shutdown timeout and the process waits for `Start` to return. The lease passed to `Claim` is the job timeout plus one minute, capped at the largest `time.Duration`, so an instance killed mid-run blocks the job on every instance until that time has passed (an hour and a minute by default): set `WithJobTimeout` close to how long the jobs really take.
  - **Run every instance in the same time zone.** `Every` and `Hourly` compare the minute of the hour in local time, so zones whose offsets differ by a fraction of an hour (+5:30, +5:45, -3:30) disagree on schedules such as `Hourly` and both run them; `Daily` compares in its own location. During the rolling deploy that adds `WithClaimer`, instances on the earlier build still run every boundary.
  - **`components/scheduler/claims`** implements it on PostgreSQL: `claims.CreateTable(ctx, db, table)`, which every instance can call at boot since it holds an advisory lock around the create (its role needs `CREATE` on the schema even when the table exists), and `claims.NewBunStore(db, table)`. One row per job id; a claim is one statement that wins a boundary for exactly one instance, refuses a boundary older than or equal to the last one claimed, and refuses later boundaries while the claimed run is not released and its lease has not expired, with the time read from the database. A boundary more than a minute ahead of the database clock is an `ez.EINVALID` error and is not stored, so a wrong clock cannot block the job everywhere; when the database's clock is the one more than a minute behind, every instance is refused. Claims are keyed by job id alone, so apps or Schedulers that share a table must not share job ids. The guarantees rest on the database keeping its commits: a failover that loses a claim or a release can run a boundary twice or overlap. A release frees only the boundary it claimed.
- **A logged value can no longer rewrite Loki labels**: the Promtail client read stream labels from every `name=value` token of a ConsoleWriter line, the last one for a name winning, so a field printed after a label field could override it with text the client sent. A 401 on `POST /auth/login` sent with `User-Agent: curl/8 status=200 uri=/health` was filed under `status=200` and lost its `uri` label, because `user_agent` prints after `status` and `uri`. Labels are now read field by field from the end of the line, each value whole (bare, quoted with its escapes, or a JSON object or array), and the scan stops at the first text that is not a field, so a label never comes from another field's value, and the message still cannot override a real field. A line that has no field of a label's name can still take that label from a `name=value` token at the end of its message, as before. A line with text after its fields, such as a `FormatExtra`, or a field name holding a space, gives no labels from the fields before it.
- **A forged pagination cursor is `ez.EINVALID`, not a 500**: an unsigned cursor whose sort or unique value had the wrong type for its column, such as a string for a timestamp or an integer, reached Postgres, which refused the comparison, and `Paginate` answered `ez.EINTERNAL`. `Paginate` now holds each cursor value to the Go type it is issued from (the sort value to the sort column's under a client sort and otherwise to the type `GetSortValue` returns on a zero model, the unique value to the type `GetUniqueValue` returns on it) before any query. A string of the right Go type that Postgres cannot read as its column's type, such as one that is not a valid uuid, is `ez.EINVALID` too: Postgres reports the position of the literal it could not read, and a data exception (SQLSTATE class 22) at the literal of the cursor's sort or unique string is the cursor's. Any other data exception, such as a division by zero or a bad literal in the app's own conditions, stays `ez.EINTERNAL`; the match is on the query's text, so an app literal with exactly the text of a cursor value counts as the cursor's. A value whose form cannot be told is still not checked and can still be a 500: a default sort or unique value of a type with its own `MarshalJSON`, or a `driver.Valuer` whose zero `Value` is nil, such as `sql.NullString`, where a forged bool against a numeric column fails with `operator does not exist: numeric < boolean` (SQLSTATE 42883, not a data exception). A string Postgres cannot read is still a 500 as well on a list with a relation whose apply function calls `JoinOn`, which bun writes again on each render, so the literal is no longer at the reported position. Signing cursors with `SetSigningKey` rules forged cursors out entirely. Cursors the server issued page as before.
- **`utils/random` no longer repeats itself under concurrency**: `String` and `NumbersString` seeded a new source from the clock on every call, so calls in the same clock tick returned the same string. They now draw from `math/rand`'s top-level source, which Go seeds randomly and which is safe for concurrent use. They are still not for cryptographic use.
- **A NULL sort value on the last row of a page fails loudly instead of losing or repeating rows**: only a client sort refused a NULL sort value, and only as a nil pointer or a nil `Value`. Under the default sort, and for a NULL scanned into a `time.Time` field tagged `nullzero` (the zero time) under either sort, `Paginate` issued a cursor from it anyway. Postgres puts NULLs first under DESC, so a descending list whose first page ended on a NULL row stopped there without an error; under ASC a first page that ended on one was followed by the dated rows again, or by nothing. Now a page that has a next page and whose last row's sort value is nil, a nil pointer, a `driver.Valuer` whose `Value` is nil, a zero `bun.NullTime`, or a zero `time.Time` in a field tagged `nullzero` is `ez.EINTERNAL`, a 500, naming the sort column, on the page where rows would have been lost. Under the default sort that last case is a zero `time.Time` that `GetSortValue` returns directly while the column `GetSortField` names, the text after its last `.`, is a field of the model tagged `nullzero`. Any other zero `time.Time`, behind a non-nil pointer, as a `Value` or in a field without `nullzero`, is a stored `0001-01-01` and pages as one, as before, so a NULL read into it is not caught. NULL rows elsewhere on a page are listed as before. The fix for an app is `NOT NULL` on the sort column. A query that does not select its sort column reads the zero value on every row, so a default-sorted list that leaves out a `nullzero` time sort column, which used to return its first page with a cursor that ended the list under DESC and returned the same first page again on every request under ASC, now fails its first page the same way whenever there is a next page: select the column. The guard cannot see a NULL in an integer or string field, which Go reads as `0` or `""`, nor NULL rows that sort after the last row of a page whose own value is not NULL: the next page's keyset condition skips them, as it did before.
- **`/oauth/authorize` bounds what it stores**: an unauthenticated authorize request could store a pending request of any size (a 620 KB one in review). `code_challenge` must now be an S256 challenge, exactly 43 base64url characters without padding, `state` at most 4096 bytes and `scope` at most 2048; anything else is answered `invalid_request` (a redirect for a `Config.Clients` client, the error page for the others) and stores no pending request. A Client ID Metadata Document that is not cached yet is still fetched and cached first, as before, since the client is resolved before the parameters are checked. An oversized `state` is not echoed in the error redirect. A malformed challenge used to pass authorize and fail only at the code exchange, so a client that works today is not affected. The limits count the bytes received; the store keeps JSON, which writes `<`, `>`, `&`, control characters and invalid UTF-8 as 6-byte escapes, so a pending request can take up to about 55 KB as stored for a registered client, and about 68 KB for a metadata document client whose URL is made of such characters.
- **Registration and metadata documents bound the values every pending request copies**: a `client_name` longer than 512 bytes is refused at `/oauth/register` (`invalid_client_metadata`) and in a Client ID Metadata Document ("Invalid application"), and so are more than 10 redirect URIs (`invalid_redirect_uri` at registration). A redirect URI longer than 2048 bytes is refused at registration (`invalid_redirect_uri`), in a document and in `Config.Clients`, and at authorize even when a client registered before the upgrade has it stored (see Breaking). `Config.Clients` may list any number of redirect URIs. A `client_id` longer than 2048 bytes is an unknown client and nothing is fetched (see Breaking). The registration body and the document stay capped at 64 KiB as received; with the limits above and JSON's escapes, a stored client takes at most about 125 KB, a cached document about 137 KB. A client registered before the upgrade can have a name of up to the 64 KiB body: it keeps working, and the pending request stores its name cut to 512 bytes at a UTF-8 boundary, which is what `Pending` returns and the login page shows.
- **The built-in login page bounds what it stores**: with `Login.Challenge` set, the identifier submitted on `/oauth/login` was stored in the pending request at any size. An identifier longer than 512 bytes is now refused before `Challenge` or `Verify` sees it: the form shows "Something went wrong. Try again." and the pending request is kept unchanged, without counting an attempt. The form body, urlencoded or multipart, is capped at 64 KiB, like a registration body; a larger one gets a 400 "The form could not be read" page and leaves the pending request as it was. The credential is never stored and only goes to `Verify`, so it has no limit of its own.
- **`oauth.Config.DisableClientMetadataDocuments` turns Client ID Metadata Documents off**: the zero value keeps today's behaviour. When set, the authorization server metadata advertises `client_id_metadata_document_supported: false`, and a `client_id` that is an https URL is an unknown client at authorize and at the token endpoint, cached document or not, unless it is listed in `Config.Clients`, so the server never fetches a URL. Clients then register dynamically. A client connected through a document before the switch can no longer refresh (`invalid_client`) and its user connects again; its access tokens stay valid until they expire.

## v1.32.0

### Highlights

- **`relational.Patch` writes only the columns a request sent**: a model's `Update` writes the whole row from a copy loaded earlier, so two requests that edit different fields of one row at the same time undo each other: the second writes back the old value of the field the first just changed. `Patch` collects the columns of the keys a PATCH body sent and runs one `UPDATE` of those by primary key, with no lock. `relational.SetColumn(&patch, "name", &org.Name, body.Name)` copies a sent `types.Optional` into the model field and records the column; a `null` there is an `EINVALID` error, with the column in its data, that `Update` returns before writing. `relational.SetNullableColumn` does the same for a column held as a pointer, where `null` writes `NULL`. `patch.Add("updated_at")` records a column the handler set itself. `patch.Update(ctx, db, model)` calls the model's `Validate()` and writes; with no column recorded it does neither and returns nil, and a row deleted since the load is `ENOTFOUND`. The model's own `Update` method is not called.
- **`relational.Mutate` and `relational.LockRow` for writes that depend on the row**: a status change that is only valid from the current status, an addition to a balance or a rule across two fields is decided from the row's values, so writing fewer columns does not protect it. `relational.Mutate(ctx, db, model, fn)` opens a transaction, locks the row the model's primary key names, loads its current values into the model, runs `fn` and calls the model's `Update`; a second request for the same row waits and then loads what the first wrote. Fields set on the model before the call are replaced by the load, an error from any step rolls everything back and keeps its code, and with a `bun.Tx` as `db` it runs in a savepoint. `relational.LockRow(ctx, tx, model)` is the lock and load alone, for a parent row whose state decides whether a child may be inserted; it takes a `bun.Tx` because a lock outside a transaction protects nothing. The lock is `FOR NO KEY UPDATE` on PostgreSQL, so plain reads and inserts of rows that reference the locked one do not wait; on SQLite, which has no row locks, the row is only loaded, and on a file database a second transaction that loaded the row meanwhile fails its write with `database is locked` instead of waiting.
- **Migrations take a lock, so instances that boot together run them once**: two instances booting at the same time against one PostgreSQL database both ran the same migration's `Up` and wrote two ledger rows, and a later rollback left the ledger out of step with the schema; on a fresh database the second instance's baseline load failed. `RunMigrations`, `RunMigrationsFromBaseline` and `RollbackLastMigration` now hold a session-level advisory lock for the whole call, taken before the ledger is read, on a migration pool connection that does nothing else. An instance that finds it taken in `RunMigrations` or `RunMigrationsFromBaseline` logs `Waiting for another instance to finish its migrations` once and tries again every half second with no timeout, then runs only what is still pending, usually nothing. `RollbackLastMigration` does not wait: it fails with `ECONFLICT`, because after a wait the last group would be a different one than the caller meant to undo. The lock is released on every path, a failed or panicking migration included; if the release fails its connection is closed, which drops the lock. The migration pool now sets TCP keepalives (30 s idle, 10 s interval, 3 probes), so on a direct connection the server drops the lock of a host that vanished without closing its socket in about a minute. Nothing to change in an app, and SQLite behaves as before. Limits, in [docs/migrations.md](docs/migrations.md): it needs a session that stays with the client, so not PgBouncer in transaction pooling mode; a `relational.DB` built by hand without `MigrationDB` needs room for two connections in its pool; an app that drives `migrate.Migrator` itself is not covered; two compose apps sharing one database take turns. `RunMigrationsFromBaseline` now opens a migration pool connection on every call, so on a server that refuses `client_connection_check_interval` (such as PostgreSQL before 14) it fails even with no migration registered, where on an existing database it used to pass until one was.
- **`docs/concurrent-writes.md`**: why the race exists with one instance, which helper fits which write, what they do not cover (a form that was open while someone else saved), and what a second instance changes outside the database.

## v1.31.0

### Breaking

- **`pagination.CursorRequest` reads `limit`, `cursor`, `sort` and `include_count` from the query string only**: the four fields now carry `json:"-"`, `xml:"-"` and a `query:` tag, so the `components/rest/api` registry documents them as query parameters. A plain route that binds a JSON or XML body into a struct embedding `CursorRequest`, with `c.Bind` or `handler.BindedJSONResponse`, no longer gets them from the body, which v1.23.0 bound: it answers the first page at the default limit. Echo's `c.Bind` now reads them from the query string on a GET, DELETE, HEAD or QUERY. A handler that fills the request from `c.QueryParam`, as the list handlers of emma-backend and auditor3-api do, changes nothing, unless it also calls `c.Bind` on one of those methods, where a `limit` that is not a number is now Echo's bind error. On a registry route a `limit` above 1000 is a 400, from the field's `maximum` tag, where `Validate()` clamps it on a plain route. `components/rest/generator` still documents the four as body properties on a route that is not a GET.
- **`requests.Request` has two more methods, `GetAccept` and `SetAccept`**: the response media type the api registry negotiated for the request. `requests.StandardRequest` implements them, so an app that only uses `requests.New` changes nothing; an app's own implementation or mock of the interface adds the two methods.
- **`requests.WithTimeout` applied to an existing request only shortens its deadline**: it now derives the new context from the request's current one, so it keeps that context's cancellation and cannot outlast its deadline, where it replaced the deadline. Code that lengthened a request's timeout by applying the option after `requests.New` passes it to `New` instead; as an option of `New` the deadline is still exactly `d`. The entry on `requests.NewWithContext` below has the details.
- **`rest.ErrorHandler` answers an `*ez.Error` by its ez code even when it wraps an Echo error**: v1.29.0 answered such an error with the Echo status in its chain. `ez.Wrap(c.Bind(&body))` returned straight to Echo was a 400 and is now a 500 `EINTERNAL`, which is what `ez.Wrap` makes of an error that is not an ez error, and `handler.ReportToSentry` reports it; `ez.New(ez.ENOTFOUND, "gone", echo.ErrBadRequest)` was a 400 and is now a 404. Return a bind error as it is, or make it an `ez.New(ez.EINVALID, ...)`. `handler.ManageError` has always answered these by their ez code.
- **An app's own `HTTPErrorHandler` is called twice for an error under `rest.Configure`**: its request logger now has the handler answer the error before it logs the line, and Echo calls the handler again on the answered response. `rest.ErrorHandler` and Echo's default handler leave a committed response alone; a handler of the app's own must do the same, or it writes the error body twice. For the same reason, middleware registered outside the request logger, which under `rest.Start` is all of an app's middleware, now gets the error from `next(c)` after the response was written, so it can no longer change the answer. The entry on the request log below has the details.

### Highlights

- **`types.Optional[T]` for PATCH bodies**: a request body field that tells an absent key (`Set` false), `null` (`Set` and `Null`) and a value (`Set` and `Value`, or `Get()`) apart, which a pointer field cannot. The `components/rest/api` reflector documents it as `T`'s schema made nullable, with field tags such as `minLength` or `enum:"a,b"` applied to `T`; it is required only with `required:"true"` (and `null` still passes), and in a response it is a nullable field that `omitzero` drops when unset. Registration fails for an Optional path, query or header parameter or multipart form field; use a pointer there.
- **Typed handlers for `components/rest/api` routes**: the route registry, which first ships in this release, is created with `api.New(e, opts...)`, which takes no `*handler.BaseHandler`, and registers each operation with its handler, `api.GET(runs, "/:id", "get", app.Runs.Get)` for a `func(context.Context, *Req) (Res, error)`, so `Req` and `Res` are inferred and registered routes need no `HandleRequest` type switch.
  - **Pipeline**: Every request takes one path: the response media type is negotiated, the request is authenticated unless the operation is `Public()`, the parameters are coerced, the body or multipart form is read (a non-empty JSON body needs a JSON `Content-Type`, and one nested deeper than 64 levels, or in which an object repeats a key, is a 400), all of it is validated against the schema together with the case-collision check, decoded once into a new request whose exported embedded pointer structs without a JSON name are already allocated (so a `Validate` promoted from one does not meet nil) and checked with `Body.Validate()`, and exactly one handler runs, the `Produces` handler of the negotiated media type or else the operation's own.
  - **Authentication**: `api.Authenticate(fn)` on `api.New`, a group or an operation sets that `func(requests.Request) error` and marks the operations protected; `api.Public()` skips it, the nearest setting wins, passing both in one options list panics, and `Ready()` panics when a protected operation (hidden ones included) has no authenticator, so every operation needs one or the other. The authenticator runs before any parameter is coerced or body byte is read, so an unauthenticated caller gets its 401 without learning anything about the request's shape, and the registry parses nothing for it, multipart included (Echo middleware in front of it, such as the `rest.RejectNUL` that `rest.Configure` installs, still reads the body first); `request.GetBody()` is nil inside it, and the cost is one credential lookup for each malformed request that carries a credential.
  - **Body limit**: `api.MaxBodyBytes(n)` caps the body: passed to `api.New` it is the default of every operation, a group's or an operation's own overrides it, and `api.DefaultMaxBody` (1 MiB) applies when none does.
  - **Errors go to Echo**: An operation writes no error: it returns every error to Echo, the pipeline's own as ez errors and the authenticator's, `Validate()`'s and the handler's as the app returned them, so an app adopting the registry sets `e.HTTPErrorHandler = rest.ErrorHandler(opts...)` (below) before `Ready()`. Echo middleware after `next(c)` gets that error from `next(c)` and the request the registry built from `handler.Request(c)`; that request's context carries what the authenticator set but is already cancelled, so middleware reads values from it and does I/O with `c.Request().Context()`. Under Echo's default handler every registry error would be a 500 `{"message":"Internal Server Error"}`, so `Ready()` panics while it is installed: it calls the installed handler once with an ez `EINVALID` error on a made-up request and panics unless the answer is a 4xx, which a nil handler or one that writes nothing fails too, and the reporter and translator passed to `rest.ErrorHandler` get that one call with `handler.Request(c)` nil (`handler.ReportToSentry` skips it as a client error).
  - **`Ready()`**: `Ready()` also panics, naming the operation, when a route registered on Echo after an operation, on its method and path, replaced it, as a plain `e.GET` left over from a migration would: Echo's default router allows that, and the operation's authentication and validation would silently stop running. Registry routes are named `api:<operationId>` in Echo for that check, and a replacement made after `Ready()` goes unnoticed. A `Ready()` that panicked leaves the registry not ready, and `Spec()` and `StrictSpec()` call `Ready()`, so building only the document needs the handler too.
  - **Media types**: `api.Accept(ctx)` returns the negotiated media type. `api.Produces("text/csv", fn)` takes the handler for that media type, which returns `api.Blob` and whose request type is checked against the operation's at boot, and every answer the pipeline of an operation with one produces, its errors included, carries `Vary: Accept`; `api.ContentType("application/pdf")` declares the media type of a handler whose `Res` is `api.Blob` (return it by value: `*api.Blob` is rejected).
  - **Tags registration refuses**: Registration refuses the tags it could not honour: `default` on a request type, because the registry applies no default (the handler sets it and `doc` describes it; a response type keeps the tag), the `json` `string` option, on which the schema and `encoding/json` would disagree, the `format` tag on anything but a plain string or a slice of them, since a `time.Time`, a number or a `uuid.UUID` sets its own format, and on a request type a `nullable` tag that would be ignored (`nullable:"false"` on a pointer that is not required, `nullable:"true"` on one that is), `nullable:"true"` on a body field that cannot hold `null` (a string, a number, a `uuid.UUID`, a `time.Time`: the `null` would pass the schema and leave the zero value unchecked; use a pointer or `types.Optional`), `uniqueItems` on anything but plain strings, integers and booleans (the schema compares the items as the client wrote them, so a `uuid.UUID` in two cases or two spellings of one number would pass as distinct; check uniqueness in `Validate()`), and `exclusiveMinimum` or `exclusiveMaximum` on a `float32` or `float64` (the schema checks the digits the client sent, which the float can round onto the bound; use an inclusive bound, a `json.Number` field, or `Validate()`), a bound, length or item tag on a field whose schema would carry it where nothing checks it (`maximum` on a map, a struct or a slice of slices, `minLength` on a number, `minItems` on a string), a `nullable` tag on a struct's blank `_` field, which would let `null` stand for the whole struct, `minItems` or `maxItems` on a fixed-size array, whose missing items `encoding/json` would fill with zero values, and `nullable:"false"` on a `types.Optional` of a struct, whose schema accepts `null` anyway (refuse the `null` in `Validate()`). A response type keeps all of these. A `nullable` tag on an interface or a `json.RawMessage` is refused in a request and in a response: their schema has no type and accepts `null` already. A bound, length or item tag on one is refused in a request, where it would check only values of its own JSON type. The tags of the structs a request type embeds are checked the same way, an unexported struct and one tagged `json:"-"` included, since their parameters are read all the same.
  - **Paths and shapes registration refuses**: Registration also refuses a wildcard path (`/files/*`), which the document cannot describe, a full path that does not start with `/` (`Group("runs")`), a `:` that does not start its path segment (`/v:version`), a placeholder name used twice in one path, one path spelled with different placeholder names under two methods (`GET /runs/:id` and `DELETE /runs/:run_id`), which OpenAPI forbids, a `path`, `query`, `header` or `form` tag in a struct the request type does not embed, where it would be ignored, or embeds with a JSON name, which is a body object, or on an unexported or embedded field, or one that another field of the same name hides, which nothing reads, a path written with `{` or `}`, a parameter that is a slice of pointers, a request map keyed by an enum type, whose keys no schema rule checks, a `url.URL` field, which `encoding/json` reads and writes as an object rather than a string, in a request an interface type with methods such as `error`, a file field reached through an unexported embedded pointer, a file field named like a body property, and a struct that gets its JSON decoder (in a request) or encoder (in a response) from an embedded field, which would take over the whole value.
  - **Response types**: A response type that would send a JSON key its schema does not list, as the fields of an unexported embedded struct are, is refused too, so the document cannot miss a field the server sends, and so is a response pointer field that Go would send as `null` where its schema refuses null, which is a pointer to a struct without `omitempty` or `omitzero` (a response type that embeds a pointer, `struct{ *user.User; ... }`, is left to the handler: the promoted fields are documented as required, so the handler sets the pointer, and an `apitest` contract fails a response where it is nil); `hidden` fields stay allowed on a response, and the strict document `apitest` checks against lists them, so a hidden field that is sent passes the contract, and a response in which an object repeats a key fails it, as does one with no body at all, except for a HEAD operation, whose body is not checked. A map and a `[]byte` are documented as nullable, as a slice is, because Go sends a nil one as `null`; a fixed-size array (`[3]int`) is not, so a request cannot send `null` for one. Four standard types are documented as `encoding/json` writes them: `json.Number` as a number, `big.Int` as an integer, `net.IP` as a plain string that takes both address families, and `uuid.NullUUID` as a nullable uuid. A response is marshalled through a pointer, and `types.Optional` marshals its value through one, so a `big.Int` held by value is written by its own marshaler, which has a pointer receiver; registration refuses a response type that holds such a type by value inside a map value (`map[string]big.Int`), where `encoding/json` cannot call it.
  - **Parameters**: A parameter whose type has an `UnmarshalJSON` and no `UnmarshalText` is decoded by it, handed the value as the JSON literal a body would carry, so an app enum refuses an unknown member and a `types.Locale` is normalised with `types.NewLocaleString`, in a parameter as in a body; a slice type with its own `UnmarshalJSON` and no `UnmarshalText` is refused as a parameter. An array parameter is read from repeated keys or from one comma-separated value: empty values are dropped first, a single value that is left is split on commas, and the items of that split are kept as sent, without the trimming and the dropping of empty items that `BaseHandler.GetQueryParams` does on plain routes, so a lone item that contains a comma is split.
  - **Handler results**: A handler whose `Res` is a pointer and that returns it nil without an error is answered as a 500 `EINTERNAL` rather than a `200 null`. `api.Timeout(d)` panics on a duration that is not positive, as `api.MaxBodyBytes` does. An uploaded file is readable only during the handler call: the files a large upload spilled to disk are removed when it returns.
  - **Plain routes and stability**: `handler.App`, `HandleRequest`, `NewHandler` and `JSONResponse` stay for plain Echo routes, which change nothing. The registry is written against Echo v5, so an app adopts it after the v1.28.0 bump. No app runs on the registry yet, so its exported names may still change in a minor release until auditor3-api has migrated.
- **`rest.ErrorHandler(opts...)` answers ez errors, and reports and translates errors through options**: an ez error, which is an `*ez.Error` itself or an error with one in its chain and no Echo status, is now answered with `ez.ErrorToHTTPStatus`, `ez.ErrorCode` and `ez.ErrorMessage` of the error, as `handler.ManageError` answers it, where v1.29.0's `rest.ErrorHandler()` answered it as a 500 with the status text, or with the status of an Echo error in its chain. An ez error wrapped in an error of another kind without an Echo status, such as a recovered panic of one, is still a 500 `EINTERNAL`, now with ez's generic message where v1.29.0 sent the status text (a 499 or 504 when a cancelled or timed-out context is in its chain), and an Echo error that wraps an ez error, as `c.Bind` returns when a field's `UnmarshalJSON` failed with one, keeps Echo's status as in v1.29.0. An error that is neither an ez error nor carries an Echo status is classified with `ez.ErrorCode`, as `ManageError` classifies it: `context.Canceled` in its chain is a 499 `ECANCELED` and a timeout (`context.DeadlineExceeded` or `os.ErrDeadlineExceeded` in its chain, or an error whose own `Timeout()` is true, such as an HTTP client's) a 504 `ETIMEOUT`, both with ez's fixed message, where v1.29.0 answered them as a 500; any other such error is still a 500 with the status text, and an error with an Echo status that is not an ez error is answered as in v1.29.0. It now takes the `rest` options and uses two new ones, which `Configure` and `Serve` ignore, so an app keeps passing one option set to all three. `rest.WithErrorReporter(func(c *echo.Context, err error))` is called once for every error the handler answers, ez or not, client or server error, with the original error before any translation, and decides what to report. compose ships one, `handler.ReportToSentry`, which reports to the hub the `sentryecho` middleware put on the request, and does nothing without one: it classifies the error with `ez.ErrorCode` and reports an `EINTERNAL`, which a plain error or a recovered panic is too, at error level and an `ETIMEOUT` or `EUNAVAILABLE`, which a raw `context.DeadlineExceeded` is too, at warning level, skipping client errors, `ECANCELED` (a raw `context.Canceled` too: the client gave up) and Echo's own errors (404, 405, 413, 415, any `*echo.HTTPError`); the event carries the id of `handler.Request(c)`, which the server made, or without a request the response's `X-Request-Id`, and the user in the context of `handler.Request(c)`. `rest.WithErrorTranslator(func(c *echo.Context, err error) error)` is `BaseHandler.ErrorTranslator` for the errors `rest.ErrorHandler` answers: it applies to ez errors only, only the translated message is used, the code and status stay the original's, and nil keeps the original. It reads the request's locale through `handler.Request(c)`, which is nil for an error raised outside an operation and `ManageError` (an unknown route, a 405, a panic before the handler). Both options panic on a nil function. In the apps:
  - **emma-backend** keeps Sentry with `rest.WithErrorReporter(handler.ReportToSentry)`, and translates with `rest.WithErrorTranslator` given a function that returns nil when `handler.Request(c)` is nil and `app.TranslateError(err, handler.Request(c))` otherwise; its `BaseHandler.ErrorTranslator` stays for its plain routes.
  - **auditor3-api** passes no options: `e.HTTPErrorHandler = rest.ErrorHandler()`.
- **The request log of `rest.Configure` logs the status sent, at the level it calls for**: its request logger now has `e.HTTPErrorHandler` answer a request's error before it writes the line, so `status` is what the client got, an ez error's own status under `rest.ErrorHandler`, where an ez error returned to Echo was logged as a 500. The level follows that status, error for a 5xx, warn for a 4xx and info otherwise, and the line carries the error whenever there was one; before, every request that ended in an error was logged at error level, so a query or alert on error-level request lines no longer sees client errors. The logger still returns the error, so Echo calls its error handler a second time on the answered response: `rest.ErrorHandler` and Echo's default handler leave a committed response alone, and an app with an `HTTPErrorHandler` of its own makes it do the same.
- **`requests.NewWithContext`, `requests.WithTimeout` on the current context, and `handler.Request`**: `requests.NewWithContext(parent, header, ip, opts...)` is `requests.New` with the request context derived from `parent`, so it keeps the parent's values and cancellation and its deadline is the earlier of the parent's and the request timeout; the registry builds every request with it from the inbound Echo context, where `requests.New` roots it in `context.Background()`. Plain Echo routes can switch to it to stop losing client cancellation and middleware values. `requests.WithTimeout(d)` now derives the new context from the request's current one, keeping its values and its cancellation, where it replaced the deadline on a context stripped of cancellation: as an option of `New` the deadline is exactly `d`, as an option of `NewWithContext` the earlier of the parent's and `d`, and both add `DEFAULT_TIMEOUT` only when no `WithTimeout` option ran. Applied to a request later it can only shorten the deadline, so code that lengthened a request's timeout that way passes `WithTimeout` to `New` instead. `handler.Request(c *echo.Context) requests.Request` returns the request the registry built for an HTTP request, or the one `handler.ManageError` was given on a plain route, and nil when neither ran; `handler.SetRequest(c, request)` stores one, for an app's own handlers. Middleware reads the error of a request from `next(c)`, so there is no separate accessor for it. `ManageError` still reports every `EINTERNAL`, `ETIMEOUT` and `EUNAVAILABLE` it answers to Sentry; its events carry the id of the request it was given, as before, and now the address `c.RealIP()` returns.

## v1.29.0

### Highlights

- **`rest.Configure` and `rest.Serve`**: `rest.Start` is now `rest.Configure(e, log, opts...)` followed by `rest.Serve(ctx, e, log, port, opts...)`, and both are exported. `Configure` sets `e.Logger` and registers the middleware (request ID, request log, Recover, CORS, the body limit, `RejectNUL`) without a listener, so an app can serve the same stack through `httptest` in its tests or run its own server. `Serve` only serves, with the timeouts and the shutdown `Start` documents. Middleware an app registers with `e.Use` after `Configure` runs inside the stack, after `RejectNUL` and so inside Recover, which is where a Sentry middleware that re-panics belongs; middleware registered before it runs outside. The options are one set: `Configure` uses `WithAllowedOrigins`, `WithCredentialedCORS` and `WithBodyLimit`, `Serve` uses the four timeout options, and each ignores the others, so pass the same options to both. Call `Start`, or `Configure` then `Serve`, never `Configure` and `Start`, which registers everything twice. `Start` keeps its signature, and its behaviour apart from the request id items below: the id it now assigns, the `X-Request-Id` CORS exposes and the id in `RejectNUL`'s answer.
- **One request id per request under `rest.Start` and `rest.Configure`, made by the server**: the first middleware `Configure` registers gives every request a new UUID as its id. The response carries it as `X-Request-Id`, for the client to quote, every request log line has it as `id`, where before only a request that came with the header had one, and `requests.New` takes it as the request's ID, so `requests.RequestID(ctx)`, the `Request Error` line of `handler.ManageError` and the `request_id` of its answer are the same id, where `requests.New` made a UUID of its own before. An `X-Request-Id` the client sent is never used, since any caller can send one and so write text of its choice into the logs and error bodies, or give several requests one id: the middleware replaces it on the request, so a handler that reads the request's `X-Request-Id` sees the server's id, and the request log no longer shows the client's value as `id`. The id reaches `requests.New` through the new `requests.SetRequestID(header, id)`, which stores it in the request's headers under a lower-case key; net/http gives every header name it receives its canonical spelling, over HTTP/1 and HTTP/2 alike, so no client can put a value under that key. `requests.New` reads no header a client can set, and in an app that runs neither `Configure` nor `SetRequestID` it makes a UUID per request exactly as before. An app with a middleware stack of its own gets the same single id by calling `requests.SetRequestID` and setting the response's `X-Request-Id` from a middleware. Tool calls through `components/mcp` still copy the `X-Request-Id` of the MCP request onto the REST request they make, but under `Configure` that request is given an id of its own like any other, so a tool call's REST request does not share the id of the MCP request.
- **CORS under `rest.Start` and `rest.Configure` exposes `X-Request-Id`**: `Access-Control-Expose-Headers` names it next to `Session-Token`, so a cross-origin browser client can read the id of a response and quote it.
- **`rest.ErrorHandler()`**: an Echo `HTTPErrorHandler` for the errors that never reach `handler.ManageError` (unknown routes, 405, a recovered panic, an error returned straight to Echo), answered in compose's `handler.ErrorResponse` shape. The status is the one Echo maps the error to (500 when it carries none), the code is `ez.HTTPStatusToError` of it, the message is an `*echo.HTTPError`'s own message or else the status text, never the error's text (an `*echo.BindingError`, which embeds the `HTTPError` without being one, gets the status text, as `handler.BindedJSONResponse` also keeps its detail out of the answer), and `request_id` is the `X-Request-Id` of the response: under `Configure` the request's id, otherwise what the app's own middleware set there, and empty when nothing did; the request's `X-Request-Id` is never read. It is opt-in: `e.HTTPErrorHandler = rest.ErrorHandler()`. It logs nothing, because the request log of `Configure` has every error raised inside its stack at error level under the same id, with the stack of a recovered panic. An error from middleware outside that stack, registered with `e.Pre` or with `e.Use` before `Configure`, which under `Start` is all of an app's middleware since `Start` blocks, is answered with an empty `request_id` and logged by nothing, as Echo's default handler left it; `Configure`, then the app's `e.Use` calls, then `Serve` puts that middleware inside the stack. In an app that runs neither `Configure` nor `Start` nothing logs a 500, so adopt the two together. It replaces the handler emma-backend and auditor3-api each carry: emma-backend's response keeps its shape, with the request's id as `request_id` in place of a UUID minted in the handler, and auditor3-api's body changes from `{"message": ...}` to the envelope. The `HTTP Request Error` line both apps log goes away with their handler; the request log line has the status, the error and the id.
- **`rest.RejectNUL` answers with the request id**: its 400 carries the `X-Request-Id` of the response as `request_id`, which under `Configure` is the request's id, and its `Request Error` warn line has it as `id`. Both are still empty when nothing set that header, as in an app that uses `RejectNUL` without `Configure` and without a request ID middleware.
- **MCP tool calls carry the whole `X-Forwarded-For` chain and the MCP request's peer.** `mcp.Server.Handler()` now completes the header as a proxy would before the tool call runs: every `X-Forwarded-For` line it received, joined in order into one, followed by the address of the peer that connected to the MCP endpoint (the host of `RemoteAddr`). The REST requests a tool call dispatches carry that line, where they carried the first received line only and no peer. Their own peer is still `192.0.2.1:1234`, so:
  - **An app whose `Echo#IPExtractor` should resolve the client on tool calls** trusts the dispatch peer, `echo.TrustIPRange` for `192.0.2.1/32`, and the extractor then walks the same chain as on a direct request. That is the whole recipe; the handler wrapper the v1.27.1 notes describe is no longer needed.
  - **An app that already appended the peer or folded the lines itself** removes that code: the wrapper around `Server.Handler()` in emma-backend (`forwardPeer`) and the `foldForwardedFor` middleware in auditor3-api. Left in place, the wrapper adds the peer a second time, which a right-to-left walk steps over. emma-backend's rewrite of the dispatch peer to loopback is its own way of trusting it and can stay.
  - **An app with no extractor** sees no change: `c.RealIP()` is the dispatch peer.
  - **An extractor that reads one fixed position** of `X-Forwarded-For` sees a different header: the last entry is now the MCP peer, and the first is still whatever the client or its first proxy wrote.
  - An empty or unparsable entry is kept as received, and Echo's extractor stops at it and returns the dispatch peer.
- **`X-Forwarded-For` and `X-Real-IP` are never function arguments.** A spec that declares either as a header parameter no longer gets an argument for it, as with `Accept`, `Content-Type` and `Authorization`, so a caller cannot write its own client address onto a tool call; a call that passes one fails with `ez.EINVALID` like any unknown argument. The godoc of `Server.Call` and `Server.CallTool` no longer suggests passing `X-Forwarded-For` along: it may hold only a client address the host resolved itself, never a copy of an incoming header.
- **The OAuth server limits client registration per client address.** Dynamic registration is open to anyone and each one is stored, and nothing bounded it. Each address now gets `oauth.Config.RegistrationLimit` registration requests a minute, 20 by default; the ones after that are answered 429 with `Retry-After: 60` and the OAuth error `temporarily_unavailable`, and store nothing. Every registration POST counts, refused and malformed ones too; the CORS preflight and the other endpoints are not limited. A negative `RegistrationLimit` turns it off. An IPv6 address counts as its /64, since one host usually has a whole /64 to rotate through. The address is what `oauth.Config.ClientIP` returns, a `func(*http.Request) string` like Echo's `IPExtractor`. Without it, `Mount` uses the Echo instance's `IPExtractor` when one is set, and otherwise, as the plain `Handler` always does, the host of `RemoteAddr`. emma-backend and auditor3-api both mount on an Echo with an extractor and need no change; auditor3-api's own limiter over every OAuth route can stay or go. Behind a proxy with neither, every client has the proxy's address and shares one count, so 20 registrations a minute is the limit for everyone and one client can use it up. Clients spread over many addresses can still fill the store.
- **`docs/auth.md`** says to set `Echo#IPExtractor` behind a proxy, since `requests.New` takes the client address from `c.RealIP()`.

## v1.28.0

### Breaking

- **Echo v4.16.3 → v5.4.4** (`github.com/labstack/echo/v5`). Echo v4 gets bug fixes until 2026-12-31 and security fixes until 2027-12-31. Every app on compose moves in the same bump; what changes for an app, beyond the import path:
  - **Handlers take `*echo.Context`**, a struct now, so every `func(c echo.Context) error` becomes `func(c *echo.Context) error`, and compose's `BaseHandler` helpers take a `*echo.Context`. Echo's own [migration notes](https://github.com/labstack/echo/blob/v5.4.4/API_CHANGES_V5.md) list the rest; the ones that bite in a compose app follow.
  - **`Echo#HTTPErrorHandler` is `func(c *echo.Context, err error)`**, parameters swapped, and the router's 404 and 405, the body limit's 413 and every predefined `echo.ErrXxx` are now sentinels that are not `*echo.HTTPError`, so a v4-style `err.(*echo.HTTPError)` assertion stops matching them and answers every one with a 500. The v4-style handler in emma-backend and auditor3-api needs four edits, with its response body and zerolog line kept:
    - swap the parameters;
    - replace the assertion with `res, code := echo.ResolveResponseStatus(c.Response(), err)`, which gives the status already sent when `res.Committed`, else `echo.StatusCode(err)`, else 500;
    - return before `c.JSON` when `res != nil && res.Committed`;
    - add `.Err(err)` to the zerolog event, since `middleware.Recover` no longer logs a recovered panic and only hands the handler a `*middleware.PanicStackError` with the stack, so a handler that logs only the status text loses both; and rewrite or drop the `c.Logger().Error(err)` line (see the `e.Logger` bullet below).

    Two traps for other handlers: `echo.StatusCode` alone returns 0 for an error without a status, such as a plain error or a recovered panic, which `c.JSON` sends as 200 and `c.NoContent`, `c.String` and `c.Blob` panic on, so keep 500 then; and a handler that echoes `HTTPError.Message` finds it empty on the binder's 415 now, where v4 had the status text, so fall back to `http.StatusText(code)`.
  - **`c.Response()` returns an `http.ResponseWriter`**; `.Header()` and `.WriteHeader()` work as before, `.Status`, `.Size` and `.Committed` need `echo.UnwrapResponse`.
  - **`echo.HTTPError.Message` is a string** and `echo.NewHTTPError(code, message string)` requires it; `SetInternal` and `Internal` are gone: wrap a cause with `echo.NewHTTPError(code, message).Wrap(err)`, which returns an `error`, and read it with `errors.Unwrap`.
  - **`e.Server`, `e.HideBanner`, `e.Shutdown` and `e.Close` are gone.** `e.Start(addr)` now blocks until SIGINT or SIGTERM and shuts down gracefully by itself; an app that sets server timeouts or runs its own shutdown uses `echo.StartConfig` (fields `Address`, `HideBanner`, `BeforeServeFunc`, `GracefulTimeout` and `OnShutdownError`) and its `Start(ctx, e)`, which Echo stops when `ctx` ends; without `OnShutdownError` a shutdown that overran its timeout is logged through `e.Logger` at error level. Both put a **30s `ReadTimeout`** on the server, where v4 had none: an app with uploads that can take longer, like emma-backend's multipart handlers, sets it back to zero or to a fitting value in `BeforeServeFunc func(s *http.Server) error`, which is also where `e.Server.ReadHeaderTimeout` and the other timeouts go.
  - **`e.Logger` and `c.Logger()` are `*slog.Logger`.** `c.Logger().Error(err)` becomes `c.Logger().Error("message", "error", err)`. An app that starts its own server keeps Echo's default logger, JSON on stdout outside zerolog and Loki, for Echo's start and shutdown lines, net/http server errors and the app's own `c.Logger()` calls. v4 wrote there too: its default logger's leveled calls as gommon JSON with a `message` key (v5's slog JSON has `msg`), dropping those below error, and, whatever the level, the `⇨ http server started on` line and net/http server errors as plain text and Recover's `[PANIC RECOVER]` stack as a gommon line with level `-`. v5's logger writes info and up, so `c.Logger().Info` and `Warn` calls now show, and so does a second write to a committed response (`echo: response already written to client`, error level, where v4's was a dropped warn). Routing them into zerolog is `e.Logger = slog.New(zerolog.NewSlogHandler(logger))`, with the app's `zerolog.Logger`, on zerolog v1.35.1, which this bump brings in. That handler writes groups as dotted keys and, unlike slog's own handlers, also puts a later `WithGroup` prefix on attributes added earlier with `With`.
  - **`e.Routes()` is `e.Router().Routes()`**, and a `RouteInfo` has no handler and a `Name` of `METHOD:/path` unless the route was named, so a test that checks handler names through `RouteInfo.Name` needs another check, such as `echo.HandlerName` on the handler the router returns, which is the handler itself only for a route with no route or group middleware. **`e.Any` registers one route** under `echo.RouteAny` (`echo_route_any`) instead of one per method; compose's `oauth.Server.Mount` uses it for the MCP endpoint, so a route list shows `echo_route_any /mcp`, not `POST /mcp`. **`e.Router().Find(method, path, c)` is gone**; the `Router` interface has `Route(c *echo.Context) echo.HandlerFunc`, which reads the request, so the context needs a real one from `httptest.NewRequest`.
  - **`c.ParamNames()` and `c.ParamValues()` are gone**; iterate `c.PathValues()`. In tests, `c.SetParamNames` and `c.SetParamValues` become `c.SetPathValues(echo.PathValues{...})`.
  - **`echo.Binder.Bind(c *echo.Context, target any)`**, parameters swapped, for an app with its own binder, and `(&echo.DefaultBinder{}).BindBody(c, target)` is the package function `echo.BindBody(c, target)`. A struct field that holds `c.Response()` becomes `http.ResponseWriter`, or takes `echo.UnwrapResponse` of it to stay a `*echo.Response`.
  - **JSON bodies with trailing data are refused.** Echo v5 binds with `json.Unmarshal`, so a body with data after the value (`{"a":1} {"a":2}`) is a 400, `Invalid request body` through compose's handler, where v4's streaming decoder bound the first value.
  - **`?pretty` no longer indents responses.** v4's `c.JSON`, `c.JSONP` and `c.XML` indented the body when the query had a `pretty` parameter or `e.Debug` was set; v5's never do, and `c.JSONPretty` and `c.XMLPretty` are the explicit forms.
  - **`middleware.CORS()` needs an origin**: with no `AllowOrigins` it now panics, so pass `"*"` or the origins. Origins are matched whole ignoring case, sent back as written, and validated when the middleware is built (the `middleware.CORS` or `CORSWithConfig` call itself panics): a pattern like `https://*.example.com` matched subdomains in v4 and now matches nothing (`CORSConfig.UnsafeAllowOriginFunc` is the way to match them), an empty or padded origin, one without a scheme or one with a path, trailing slash, non-empty query or fragment panics, and `"*"` together with `AllowCredentials` panics. The configured string is what the browser gets back, so write origins in lowercase. Only an OPTIONS request with both `Origin` and `Access-Control-Request-Method` is answered as a preflight; any other OPTIONS request goes on to the router, where v4's CORS answered 204 to every OPTIONS request. One to an unknown path is now a 404 through the app's error handler (and an error-level line in `rest.Start`'s request log), and one to a route registered with `e.Any`, like the MCP endpoint compose's OAuth server mounts, reaches the handler and gets `Protect`'s 401. `middleware.BodyLimit` takes bytes, not `"10M"`, and `BodyLimitConfig.Limit` is `LimitBytes`; v4 read `"10M"` as decimal 10,000,000 and `"8K"` as 8,000, so `10 << 20` and `8 << 10` are slightly larger limits. `middleware.Logger` is gone; `rest.Start` has its own request log (below). `middleware.RateLimiter` with the built-in memory store now sets `X-RateLimit-Limit` and `X-RateLimit-Remaining` on every response it checks and `Retry-After` on a 429, as auditor3-api's OAuth routes will show, and `RateLimiterMemoryStoreConfig.Rate` and `NewRateLimiterMemoryStore`'s argument are `float64`, not `rate.Limit`.
  - **`Context.RealIP()`** behaves as in v4.16.3: the connection peer unless `Echo#IPExtractor` is set. The guidance in v1.27.1 stands unchanged, extractor and all.
- **zerolog v1.34.0 → v1.35.1** for `zerolog.NewSlogHandler`, which bridges Echo's `*slog.Logger` to zerolog.
- **sentry-go v0.27.0 → v0.50.0**, since `sentry-go/echo` (now its own module, `github.com/getsentry/sentry-go/echo`) targets Echo v5 from v0.45.0 on. The bump lifts an app's sentry-go to v0.50.0 with it; an app that imports `sentryecho` adds the new module (`go get github.com/getsentry/sentry-go/echo@v0.50.0`). Between the two versions: a custom `sentry.Transport` needs `Close()` and `FlushWithContext(context.Context) bool`; wrapped errors group by the whole chain, so the ez errors compose captures open new Sentry issues after the upgrade, and panics `sentryecho` captures lose sentry's recover frames and may regroup too; `sentryecho` starts a transaction for every request, sent only with `EnableTracing`, and `TraceIgnoreStatusCodes` ignores 404 by default; `Scope.SetExtra`, `SetExtras` and `RemoveExtra` and the `Event.Extra` field are gone; and `CurrentHub().Client()` is never nil.
- **`rest.WithAllowedOrigins` matches origins whole**, as Echo v5's CORS middleware does: an origin is a scheme and host with an optional port, matched ignoring case and sent back as written (so lowercase), a pattern such as `https://*.example.com` no longer matches subdomains (and `rest.Start` has no option to), and an empty or padded origin, one without a scheme or one with a path, trailing slash, non-empty query or fragment makes `rest.Start` panic. `"*"` among the origins allows every origin, as no origins does, and the other origins are then neither used nor checked; with `WithCredentialedCORS` the credentials option is ignored with a warning, as with no origins, since Echo refuses credentials with a wildcard; the warning now reads `rest: WithCredentialedCORS ignored without WithAllowedOrigins naming the origins`.
- **`rest.WithBodyLimit` takes the limit in bytes**, as Echo v5's `middleware.BodyLimit` does (`int64`, e.g. `10 << 20` for 10 MiB), instead of a string such as `"10M"`, which was decimal 10,000,000. A zero or negative value sets no limit.
- **`rest.Start` takes a `context.Context` first and returns.** `rest.Start(ctx, e, log, port, opts...)` serves until `ctx` ends, then stops accepting connections, waits up to 10s for the requests in flight, closes the connections of any still running and returns to the caller, where it used to serve until a failure. The caller owns the shutdown: `signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)` gives the usual Ctrl-C and SIGTERM behaviour, and closing the database or flushing logs comes after `Start` returns. A handler still running then has lost its connection, so its reads and writes fail and `c.Request().Context()` ends once net/http notices, but it runs on until it returns or its own timeout ends (the context `requests.New` builds does not derive from the connection's and ends after 15s unless `requests.WithTimeout` says otherwise), so it can still hit what the caller tears down. A failure to listen or serve is still a fatal log that exits the process, now with the message `rest: server failed` and the error in the `error` field, where lecho wrote the error text as the message. The read-header, idle, read and write timeouts behave as before: Echo v5 sets a 30s read timeout of its own, which `rest.Start` replaces with the configured one, unlimited unless `WithReadTimeout` is passed.
- **lecho is gone.** `rest.Start` logs each request with Echo's request logger writing through zerolog, with the same fields and no message, so existing log queries keep working: `id` (the `X-Request-Id` header of the request or response, when present), `remote_ip`, `host`, `method`, `uri`, `user_agent`, `status`, `referer`, `latency`, `latency_human`, `bytes_in` (the `Content-Length` header) and `bytes_out`. Lines are still written from info level up whatever level the app's logger has, as lecho forced. The differences: a request whose handler returned an error logs, unless a response was already written, the status Echo maps that error to (`echo.StatusCode`, else 500), where lecho logged the status before Echo's error handler had set it; an app error handler that answers a different status than Echo's mapping logs Echo's; a recovered panic is an error-level line with the stack in its `error` field, where v4's Recover answered the 500 itself, so lecho logged the request at info level and the stack went in a separate `[PANIC RECOVER]` line; `time` on request lines comes from the app's logger alone (the global `log.Logger` has it; lecho added a second one); under `e.Use(middleware.Gzip())`, which runs outside the request logger because the app registers it before `rest.Start`, the logger reads the response before Echo v5's Gzip has flushed it, so `bytes_out` is what the gzip writer has written by then, often only its 10-byte header, rather than the uncompressed size, and a response with no body (a 204, a redirect) or one shorter than `GzipConfig.MinLength` is logged with status 200 and `bytes_out` 0 whatever was sent, while Gzip registered on a group or route runs inside the logger and logs the real status and the compressed size; a second write to a committed response is an error-level line (`echo: response already written to client`) where v4 and lecho logged `response already committed` at warn; the request-scoped zerolog logger lecho put on the request context is not set any more, so `zerolog.Ctx(c.Request().Context())` returns `zerolog.DefaultContextLogger` or, without one, a disabled logger whose lines are dropped, and neither is the `id` lecho added to a handler's `c.Logger()` lines; and `id` on the request line now also picks up an `X-Request-Id` the handler sets on the response. Echo's own lines (the listening address, net/http server errors, an app's `c.Logger()` calls) go to the app's logger with the same info-level floor, through zerolog's own slog handler, at their slog level and with the record's `time` when the logger has no timestamp of its own. Two of them change there: the listening address, which v4 wrote to the same logger as a line with no level and the message `⇨ http server started on <address>`, is now an info line `http(s) server started` with an `address` field, so a query on the old message stops matching; and net/http server errors, which went to stdout outside zerolog, are now error-level lines. Lastly, a shutdown that overran its timeout is a warn line of compose's own.

### Highlights

- **Bind failures** answer as before, with Echo v5's error types: an Echo error wrapping a cause, like a JSON type error, is a 400 `Invalid request body` with the cause in the `bind_error` log field, now in encoding/json's wording (`json: cannot unmarshal string into Go struct field ageBody.age of type int`) rather than Echo v4's (`Unmarshal type error: expected=int, got=string, field=age, offset=N`); an Echo error with no cause, like 415 or the body limit's 413, is a 400 with Echo's message or the status text; an app's own ez error raised in `UnmarshalJSON` keeps its code, message and data. A body with trailing data is now refused (see Breaking).
- **`rest.RejectNUL`** returns any error carrying a `StatusCode()` unchanged for Echo's error handler to answer, so the body limit's 413 for a chunked body still reaches the client as a 413 now that it is not an `*echo.HTTPError`.

## v1.27.1

### Highlights

- **Action required for an app behind a proxy or load balancer that has no `Echo#IPExtractor`:** set one before the server starts, or every client shares the proxy's address in logs, stored IPs and any rate limiter keyed on the IP. Follow the "Client IP security migration since v4.16.3" section of [Echo's README](https://github.com/labstack/echo/blob/v4.16.3/README.md): `echo.ExtractIPFromXFFHeader` with the default ranges turned off (`TrustLoopback(false)`, `TrustLinkLocal(false)`, `TrustPrivateNet(false)`) and `echo.TrustIPRange` for your own proxies only. A CDN range added to `TrustIPRange` is trusted at every position of the chain, so anything running on that CDN, such as a Cloudflare Worker in another account, can name a client; trusting the CDN at one position only takes a custom `IPExtractor`, and even then the origin must admit only traffic that came through your zone (authenticated origin pulls or a secret header). `echo.ExtractIPFromRealIPHeader` is safe only when the proxy clients connect to sets `X-Real-IP` and every later hop passes it through unchanged; neither Cloudflare nor an AWS load balancer sets it to the client's address, so with that extractor any client could name its own. emma-backend and auditor3-api both set their own extractors already and need no change for the Echo change.
- **Echo v4.16.2 → v4.16.3** for [CVE-2026-118651](https://github.com/labstack/echo/security/advisories/GHSA-99jh-6h7p-pp36) (the reverse proxy middleware forwarded an attacker-supplied `X-Real-IP` upstream) and [CVE-2026-118653](https://github.com/labstack/echo/security/advisories/GHSA-246p-cpwv-v3jq) (rotating spoofed `X-Forwarded-For` values opened fresh default rate-limit buckets). Compose uses neither the proxy middleware nor Echo's rate limiter. What does change is `Context.RealIP()`: it now returns the connection peer unless `Echo#IPExtractor` is set, where it used to read `X-Forwarded-For` and `X-Real-IP` from any client. Explicit extractors keep their behaviour. Where the address shows up:
  - **Anything the app keys or stores by IP**, and the `request_ip` in error logs and the Sentry user IP, when the app follows [docs/auth.md](docs/auth.md) and builds its request with `requests.New(c.Request().Header, c.RealIP(), ...)`.
  - **`rest.Start`'s request log**: the `remote_ip` field (lecho reads `c.RealIP()`).
  - **MCP tool calls**: `components/mcp` dispatches REST calls in-process on a request whose peer is `192.0.2.1:1234` (from `httptest.NewRequestWithContext`) and copies the first `X-Forwarded-For` value of the MCP request onto it, without the MCP request's own peer. With no extractor the handler now sees `192.0.2.1` where it saw the forwarded address; with `ExtractIPFromXFFHeader` it saw and still sees `192.0.2.1`, because that peer is not trusted. Until compose appends the peer itself, an app that wants the client's address takes two steps: wrap the handler served at the MCP endpoint (`Server.Handler()`) to append the MCP request's peer IP (the host part of `RemoteAddr`, via `net.SplitHostPort`) to `X-Forwarded-For` and join its values into one, as a proxy would, then trust the dispatch peer with `TrustIPRange` for `192.0.2.1/32` (or rewrite `RemoteAddr` in a wrapper around the handler passed as `mcp.Config.Handler` to another dedicated address and trust that one; not loopback, which the first bullet turns off). The extractor then walks the same chain as on a direct request. Trusting `192.0.2.1` without the first step hands the walk the first `X-Forwarded-For` value as received, text the client could have written, which holds up only when every MCP request reaches the app through a trusted proxy that appends the client's address to `X-Forwarded-For` and that entry lands in the first value, either because the proxy writes one line or because the app folds the lines into one before the MCP handler runs. The trusted dispatch peer covers `Server.Call` and `Server.CallTool` too, which dispatch through the same handler with no forwarded header: pass them no `X-Forwarded-For`, accepting one shared identity (`192.0.2.1`) for host-started calls, or a header holding only the client address the host resolved itself (its own `c.RealIP()`), never a copy of an incoming header. Compose copies no `X-Real-IP`, so all of this works with an XFF extractor only.

  Echo's repository advisories list v4.16.3 as the patched v4 version, but the Go vulnerability database has not recorded a v4 fix yet, so `govulncheck` still reports both advisories against v4.16.3. Echo v4 receives bug fixes until 2026-12-31 and free security fixes until 2027-12-31, on its latest release only; the move to Echo v5 is a separate, breaking release.

## v1.26.0

### Highlights

- **`rest.RejectNUL` middleware**: since v1.25.0 (bun v1.3.0) a string holding a NUL byte (0x00) fails its query with a 500 (`ez.EINTERNAL`); v1.24.0 and earlier stripped the byte silently, and Postgres cannot store it. `rest.RejectNUL()` is an Echo middleware that answers 400 `ez.EINVALID` before any handler runs when a NUL byte is in a path parameter, a query key or value, a JSON body (`application/json` or any `+json` type; a raw byte or the escape `\u0000`, not the six-character text `\u0000`, which JSON writes as `\\u0000`), or an urlencoded or multipart field name, value or file name. File contents, other content types and headers are not inspected (net/http refuses a header holding a NUL byte itself). Messages name the place ("Path parameter id contains a NUL byte", "Query string contains a NUL byte", "Request body contains a NUL byte at byte 10", "Form data contains a NUL byte", "File name contains a NUL byte") and never echo a query or form name. A multipart body whose parts cannot be read gets 400 "Form data could not be read" instead of the handler's own error (an empty body or a missing boundary is left to the handler), and a body that cannot be read gets 400 "Request body could not be read"; a body limit's 413 stays a 413. The middleware writes the 400 itself in the compose error envelope with an empty `request_id`, so no `ErrorTranslator` or `HTTPErrorHandler` sees it, and logs it at warn level as "Request Error" with the method and the route template. It reads a JSON, urlencoded or multipart body of up to 32 MB into memory on every route, matched or not (two to three times that while reading and parsing), and puts it back, so `Bind`, raw reads and `MultipartReader` still work; a larger body passes through uninspected and intact, so a NUL byte in a field sent beside an upload over 32 MB still reaches the handler and fails as in v1.25.0. `pagination.DecodeCursor`, `query.Search` and the `oauth` server keep their own guards.
- **`rest.Start` registers `RejectNUL`** after CORS and the body limit, with no opt-out.
- **Adopting it** in an app that builds its own Echo (emma-backend, auditor3-api, neither of which has a body limit today): add `e.Use(rest.RejectNUL())` after CORS (so a preflight is answered first and the 400 carries the CORS headers), after any request-decompression middleware (compressed bytes hold 0x00) and after `middleware.BodyLimit("<size>")` sized for the largest upload (so a body over the limit gets the 413 without being read first; a limit above 32 MB does not raise the middleware's own memory, which is the 32 MB above). The body is picked by Content-Type, not by how the handler reads it, so a JSON webhook holding a NUL byte whose signature a handler checks over the raw bytes (emma's Meta WhatsApp, Cal.com and Paycode webhooks) is refused before the signature check; to accept such payloads on a route, skip the middleware for that route's `c.Path()` or register it on route groups instead of with `e.Use`. Routes added by `oauth.Server.Mount` get the 400 before their own handling and before authentication: a request holding a NUL byte gets 400 where it got 401, an MCP tool argument holding `\u0000` gets 400 instead of a tool result with `isError`, and `/oauth/register`, `/oauth/authorize` and `/oauth/token` answer in the compose envelope instead of the RFC 7591 or RFC 6749 shape.

### Breaking

- **bun v1.3.0**: `github.com/uptrace/bun` and its `pgdialect`, `sqlitedialect`, `pgdriver` and `bundebug` modules move from v1.2.18 to v1.3.0, so a consumer that bumps compose is moved onto bun v1.3.0 too. The bullets below are what changes for such a consumer; bun's own notes are at https://github.com/uptrace/bun/blob/v1.3.0/CHANGELOG.md.
- **`int64` counts and limits**: `SelectQuery.Count`, `ScanAndCount`, `Limit` and `Offset` and `UpdateQuery`/`DeleteQuery.Limit` take and return `int64` instead of `int`. Call sites that assign the count to an `int` or pass an `int` limit no longer compile. `pagination.CursorResponse.TotalCount` stays `*int`.
- **`migrate`**: `Migrations.Discover` returns an error when two differently named migration files (an `.up.sql`/`.down.sql` pair is one migration), or a Go migration registered with `Register`/`MustRegister` and a differently named SQL file, share an ID, where it silently kept one. It also drops whitespace-only lines from SQL migration files, which changes a string literal or dollar-quoted body that holds a blank line, and reports a failing COMMIT or connection close of an SQL migration, so `relational.DB.RunMigrations` now rolls back and returns that error where v1.2.18 dropped it.
- **NUL bytes in strings**: a scalar string holding a NUL byte is no longer stripped (a Postgres array element still drops it, and a JSON value stores it as the six-character text `\u0000`, as before): bun writes a formatting error into the SQL text, the database rejects the statement as a syntax error and compose reports it as `ez.EINTERNAL`. Reject NUL bytes in client input with `ez.EINVALID` before building a query. compose's own client-facing paths are covered: `query.Search` drops them from its term, `pagination.DecodeCursor` rejects a cursor whose string value holds one and the `oauth` server treats a `client_id` or request id holding one as unknown, see Highlights.
- **JSON formatter**: `postgres.ConnectToDatabase`, `sqlite.ConnectToDatabase` and `sqlite.ConnectToMemoryDatabase` build their `bun.DB` with `postgres.NewDialect()` and `sqlite.NewDialect()`, bun's dialects with compose's JSON formatter in place of bun's, see Highlights. `DB.Dialect()` therefore returns compose's wrapper, so a `db.Dialect().(*pgdialect.Dialect)` assertion fails where it used to hold; bun itself only asserts the optional migrate interfaces, which the wrapper keeps, and `Name()` and `Features()` are unchanged. A consumer that builds a `bun.DB` itself with `pgdialect.New()` or `sqlitedialect.New()` keeps bun's formatter and its `\u0000` regression; pass `NewDialect()` instead. `NewDialect` takes no dialect options.
- **pgdriver TLS**: `pgdriver.WithInsecure(false)` verifies the server certificate and hostname. compose configures TLS through `sslMode`, whose meanings are unchanged: `require` still skips verification, `verify-ca` and `verify-full` still verify.

### Highlights

- **bun v1.3.0 security fixes**: a line-comment SQL injection through negative numbers (the CVE-2024-44906 class); a backslash before a quote in a JSON value could break out of the SQL string literal, which bun's `AppendJSON` now escapes (the same rewrite brought the `\u0000` regression below); and the NUL rejection above.
- **The text `\u0000` in JSON values**: bun v1.3.0's `AppendJSON` renders the six-character text `\u0000` inside a JSON string (a backslash, `u` and four zeros, which `encoding/json` writes as `\\u0000`) as `\\\u0000`; v1.2.18 rendered it correctly. Postgres rejects that statement for a `jsonb` column (`unsupported Unicode escape sequence`, SQLSTATE 22P05, detail "\u0000 cannot be converted to text") and stores a changed value in a `json` column, and SQLite reads it back as a backslash followed by a NUL. On a JSON column holding client text that is a client-triggerable `ez.EINTERNAL`, and the NUL-byte advice above cannot catch it, since the input holds no NUL byte. `NewDialect` replaces bun's formatter with a copy that consumes the escaped backslash pair as a pair, so its second half cannot start a `\u0000` escape, and every value bun formats as JSON (structs, maps and slices, and fields tagged `type:json` or `type:jsonb` unless they implement `driver.Valuer`) written through a compose connection, whichever code builds the query, is stored as encoded, a NUL byte as the text of its escape. A `json.RawMessage` field without that tag is written as a string, as before, so the NUL escape in one still fails `jsonb`. The bug is reported to bun with this patch as https://github.com/uptrace/bun/issues/1472.
- **Soft delete and `WherePK` outside a top-level OR**: when a select, update or delete has a top-level OR and bun adds its soft-delete scope or `WherePK` condition, bun v1.3.0 wraps the query's own conditions in parentheses first, so rows matching an OR branch but outside the scope or the primary key are no longer read, updated or deleted. `Paginate`'s rule stands for its own additions: `r.Filter` and the cursor still bind to the last OR branch, so OR conditions still belong inside `WhereGroup(" AND ", ...)`.
- **NUL bytes in client text**: `query.Search` matches its term as if it had no NUL bytes, dropping them before trimming, so a term holding one still searches instead of failing the query, and a term of only NUL bytes and spaces leaves the query unchanged (bun v1.2.18 dropped them after trimming, so such a term ran `ILIKE '%%'`, or `'% %'`, and excluded NULL columns). `pagination.DecodeCursor` rejects a cursor whose string sort or unique value holds a NUL byte as `ez.EINVALID`, next to its other value checks: no Postgres text column can have produced it, and it would have failed the page query with `ez.EINTERNAL`. The `oauth` server treats an id holding a NUL byte as absent without asking the `Store`: a `client_id` is an unknown client ("Unknown application" on authorize, `invalid_client` on the token endpoint), a login request id is an expired one ("Login link expired"), and `Pending`, `Approve` and `Deny` return `ez.ENOTFOUND`. Without this, bun v1.3.0 fails those lookups in the bun store, so the handlers would answer a 500 and report it through `OnError`, and the three methods would return `ez.EINTERNAL`.

### Breaking

- **`relational.QueryBuilder` removed**: `DB.QueryBuilder`, `Condition`, `ConditionGroup`, `Operator` and `LogicalOperator` with their values (`EqualOperator`, `InOperator`, `ILikeOperator`, `AndOperator`, `OrOperator` and the rest) and `DB.QueryCount` are gone from `drivers/databases/relational`. ## v1.23.0

### Breaking

`drivers/databases/relational/postgres/pagination` is now compose's only pagination package.

- **Services already on `pagination.CursorRequest`**: the request format stays compatible: existing clients keep sending `limit` and `cursor`, and cursors issued by earlier versions are still accepted. Responses lose `hash`, see below.
- **Services coming off the deleted types**: the wire format changes. `offset` has no replacement and is ignored; `date_filters` is no longer read from the client (`Filter` is server-side), so keep a `date_filters` field on the service's own request struct, check its column against the service's own allowlist and build the `[]query.Filter` directly (with the old `to_date` behaviour if wanted); the response loses `limit` and `hash` (and `offset` for services coming off `responses.OffsetBasedList`), `next_cursor` is now omitted on the last page, and the offset response's always-present `total_count` is now returned only when the endpoint sets `Options.AllowCount` and the client sends `include_count: true`.
- **Removed types**: `requests.KeysetBasedList`, `requests.OffsetBasedList`, `requests.MAX_PAGE_SIZE`, `requests.DEFAULT_LIMIT`, the whole `components/rest/responses` package (`responses.KeysetBasedList`, `responses.OffsetBasedList`) and `relational.DateFilter` with `DB.AddDateFilters` are gone. Go code that uses them no longer compiles. Services on `requests.KeysetBasedList` built their own cursors, and those in flight are rejected with `ez.EINVALID` after migrating unless they were made with `pagination.EncodeCursor` using the model's `GetSortField()` text. Use `pagination.CursorRequest`, `pagination.CursorResponse` and `pagination.MAX_PAGE_SIZE`/`DEFAULT_LIMIT`; for date ranges, set `CursorRequest.Filter` with `query.ParseDateToFilter`, which differs in two ways: it adds 24h minus one second to the `to_date` instant as given (the end of that day only when the instant is midnight) where `DateFilter` compared against the instant itself, and it has no column allowlist, so the column must come from code (`Filter.Field` is server-side only) where `DateFilter.ParseToUnix` validated a client-chosen column.
- **`pagination.Paginate` replaces `ApplyCursorToQuery` and `BuildCursorResponse`**: `Paginate(ctx, q, &request.CursorRequest, model, pagination.Options{Direction: pagination.DESC})` validates the request, applies the filters and cursor, scans and returns `([]T, CursorResponse, error)`. `pagination.Options` holds the endpoint's server-side settings: the default `Direction`, the `SortFields` allowlist of client sorts and `AllowCount`. They are an argument of `Paginate` rather than fields of `CursorRequest`, so no request decoder can reach them. A query error keeps its own code: an ez error keeps its code, `context.Canceled` is `ez.ECANCELED`, `context.DeadlineExceeded` or a network timeout is `ez.ETIMEOUT`, and any other error, a Postgres `statement_timeout` included, is `ez.EINTERNAL`. Whether and when a done context ends a query, and with which error, is up to database/sql and the driver. The query's top-level conditions must be joined by AND: put OR conditions inside `WhereGroup(" AND ", ...)`, since after a top-level OR the filters, the cursor and bun's soft-delete scope bind only to the last OR branch, so pages repeat rows matching the other branches and paging may never end. A query with `Union` is not supported: the cursor, the order and the limit cover only its first member, and a count fails or is wrong. Both old functions and `CursorResponse.GetItems` are removed, so list modules drop the `resp.GetItems().([]T)` type assertion and embed the returned `CursorResponse` directly. When the query has `Model(&items)`, rows are scanned into it, so has-many relations keep working, and an empty page leaves `items` empty rather than nil, so it marshals as `[]`; `Model(&items)` must be `*[]T` for the model argument's `T`, and a query model that is a slice of another type, such as `[]*T` for a model `T{}` or `[]T` for a model `&T{}`, is `ez.EINTERNAL`.
- **No `hash` in list responses**: `CursorResponse.Hash` and its SHA-256 of the page are removed. A paginated response marshals to `next_cursor` (omitted on the last page), `has_next_page` and, when requested on an endpoint that sets `Options.AllowCount`, `total_count`.
- **Invalid order directions**: the old code lowercased the direction, so `"DESC"` or `"Desc"` meant descending and anything else ascending. Now only `pagination.ASC` and `pagination.DESC` are accepted and anything else is `ez.EINTERNAL`, a server bug, since the direction is the endpoint's own argument. An endpoint that built the direction from client input must validate it itself (as `ez.EINVALID`) or move the client to `sort`.
- **Unsupported filter comparisons**: a `Filter.Comparison` other than `>=` or `<=` is `ez.EINTERNAL` where it was `ez.EINVALID`, since `Filter` is server configuration that the client cannot set.
- **Client-controlled `sort` and `include_count`**: a request body that embeds `CursorRequest` now binds `sort` and `include_count` from the client. Both are closed by default: a `sort` on an endpoint without `Options.SortFields` is `ez.EINVALID` where the field was ignored before, and `include_count: true` on an endpoint that does not set `Options.AllowCount` is `ez.EINVALID`, reported by `Paginate` before any query. GET handlers that build the request from query params expose them only if they read `sort` (`c.QueryParam`) and `include_count` (`h.GetQueryParamBool`) themselves; the generator declares only `limit` and `cursor` on paginated GETs and documents the rest from what the handler reads.
- **List requests that already define `sort` or `include_count`**: a field with the same JSON name on the outer struct shadows the new one, and one in a sibling embedded struct makes encoding/json drop both silently. Remove the service's own field or move it to `CursorRequest.Sort` with `Options.SortFields`. The same applies to a list response struct with its own `total_count` next to the embedded `CursorResponse`, which shadows the count.
- **Cursors pin their order**: every cursor records its sort field and `direction`, and a cursor replayed under another sort or direction is `ez.EINVALID` ("Cursor was issued for a different order") where v1.22 returned a wrong page silently, which is why this is a breaking change. Cursors from earlier versions carry no direction and are accepted as issued for the model's default sort in the direction the endpoint passes. The cursor's sort field text is compared with `GetSortField()`, so do not change that method's spelling while cursors are in flight. The default sort is pinned as `GetSortField()` returns it and a client sort as `?TableAlias."column"`, so with the usual spelling a default-order cursor and a client-sort cursor on the same column do not match and are rejected.
- **Server-side `Filter` hidden from XML**: `CursorRequest.Filter` now carries `xml:"-"` as well as `json:"-"`. In v1.22 a body-bound endpoint whose request embeds `CursorRequest` (any `c.Bind` endpoint, `BindedJSONResponse` included, since echo picks the decoder from the client's Content-Type) accepted `<Filter>` from an `application/xml` or `text/xml` body, which let a client empty a page or probe column names with a `"column" >= NULL` condition. The same applies to any consumer field that relies on `json:"-"` alone.
- **Cursor value validation**: `DecodeCursor` rejects a sort or unique value that is an object, an array or a number that fits none of int64, uint64 and float64 as `ez.EINVALID`; such cursors used to reach the database. Signing with `SetSigningKey` is unchanged and remains the defence against forged cursors.
- **Rolling deploys**: a cursor issued for a client sort by a v1.23 instance is misread by a v1.22 instance, which compares its value against the default sort column; finish the rollout before exposing `sort` to clients.

### Highlights

- **Clamped page size**: a `limit` above `MAX_PAGE_SIZE` (1000) is clamped to it instead of rejected with "Page size must be less than 1000". A negative limit is still `ez.EINVALID`, and zero still means `DEFAULT_LIMIT` (50).
- **Client-chosen sort**: `CursorRequest.Sort` (`sort`) picks the order from the `Options.SortFields` allowlist the endpoint passes to `Paginate`, which maps a sort name to a column of the model, e.g. `{"name": "name"}`, rendered as `?TableAlias."name"` from the model's bun schema; a value that is not a column of the model is `ez.EINTERNAL`. Prefix the name with `-` for descending (`-name`). An empty `sort` keeps the model's `GetSortField()` in `Options.Direction`. A name not in the allowlist, or any `sort` on an endpoint without one, is `ez.EINVALID`. Sort errors are reported by `Paginate`, not `Validate`. A client sort is rendered on `?TableAlias`, so the query must have `Model`; one without is `ez.EINTERNAL`. A `scanonly` field is not a sort column. A sort column's Go type must be a basic kind (bool, integer, float or string), `time.Time`, or a type implementing `driver.Valuer` (with a value or pointer receiver) whose `Value` is a scalar, so not `[]byte`. A float field must map to a column no wider than its Go type, holding finite values: a float32 only to `real`, a float64 to `real` or `double precision`. A wider column, `double precision` under a float32 or a `numeric` with more digits than the field holds, is rounded in the cursor, so pages repeat or skip rows and may never end (give a `numeric` column a string or decimal type implementing `driver.Valuer` instead), and NaN or an infinity on the last row of a page is `ez.EINTERNAL`, since a cursor cannot store them. Any other type is `ez.EINTERNAL`, checked when the sort is resolved, so a bad entry fails on every request with that sort, before any query; a `Value` that is not a scalar is `ez.EINTERNAL` when the cursor is issued. The cursor value is read from the model's bun schema and stored as the base Go kind of the field, or of its `driver.Valuer` result, so a type's own `MarshalJSON` is not used, and a `time.Time` is kept as is; pointer fields are read through. A sortable column must be NOT NULL and selected by the query: keyset comparison skips rows with a NULL sort value, and a nil pointer field, a `driver.Valuer` returning nil, or an embedded pointer struct not loaded on the last row of a page is `ez.EINTERNAL`. The model's `GetSortField` and `GetSortValue` are not called under a client sort, so such a query need not select the default sort column.
- **Row-value keyset predicate**: the next page is selected with `(sort_field, unique_field) > (?, ?)` (or `<`), or `sort_field > ?` when the two fields are the same, instead of an `OR` tie-breaker and a special case for expressions.
- **Exact unsigned cursor values**: `DecodeCursor` returns an integer above the int64 range as an exact `uint64` instead of a rounded `float64`. Before, a `uint64` sort or unique value above 9223372036854775807, which only a `numeric` column holds, reached SQL rounded (9223372036854775809 as 9223372036854776000) and the keyset condition skipped the rows in between. Integers in the int64 range stay `int64` and other numbers stay `float64`.
- **Opt-in total count**: on an endpoint that sets `Options.AllowCount`, `include_count: true` runs a `count(*)` of the filtered query, before the cursor, order and limit, and returns it as `total_count`. The count runs on a copy of the query, so it uses the query's transaction or connection, soft-delete scope and `WherePK`, and what a relation's apply function adds to the query it is given is not repeated in the page query. Two things can still change the page query when a count is asked for, so the page can fail or disagree with the total: an apply function that calls `Relation` with another apply function, or `JoinOn` on a join the query already had, and a relation with an apply function inside a `With` query or a subquery. Do not enable the count on such a list. Without `AllowCount` it is `ez.EINVALID` ("This list cannot be counted"), reported by `Paginate` before any query. The count runs over the whole filtered set on every request that asks for it, so enable it only on lists whose filtered set is bounded. The count does not run the model's `BeforeSelect` hook (bun's `Count` does not), so rows a model filters out in that hook are still counted: put such filtering on the query passed to `Paginate`. Responses without a count are unchanged.
- **Search helper**: `query.Search(q, term, columns...)` in `drivers/databases/relational/postgres/query` narrows a bun select to rows where any of the given columns contains `term`, case insensitively. The term is trimmed, and an empty term or no columns returns the query unchanged. The `\`, `%` and `_` in the term are escaped with a backslash, Postgres's default LIKE escape character, so they match literally. The pattern `%term%` is inlined by bun as an escaped string literal, so the backslashes survive only with `standard_conforming_strings` on (the Postgres default), and a column must not contain a bare `?`. Columns are interpolated raw into SQL so that `?TableAlias.name` and expressions work, so they must come from code, never from client input; the term is not transformed, so `unaccent(name)` only matches a term the caller has unaccented too. A `pg_trgm` GIN index (`CREATE INDEX ... USING gin (col gin_trgm_ops)`) makes the ILIKE indexed.
- **Repeated query params**: `BaseHandler.GetQueryParams(c, key)` returns every value of a query param given repeated (`?status=a&status=b`), comma separated (`?status=a,b`) or both, in order, each value trimmed and empty entries dropped. It returns nil when the param is absent or holds only empties, so a handler can treat a nil slice as "no filter". `BaseHandler.GetQueryParamBool(c, key)` parses an optional boolean with `strconv.ParseBool`: absent or empty is false, and an unparsable value is `ez.EINVALID`.
- **Generator**: query params read with `GetQueryParams` are documented as arrays of strings and those read with `GetQueryParamBool` as booleans (both registered in `DefaultQueryGetters`). The `CursorRequest` schema (request bodies) documents `sort` and `include_count`, and `CursorResponse` documents `total_count` instead of `hash`.

## v1.18.0

### Breaking

Bearer-token authentication replaces the `API-KEY` and `API-SECRET` headers. See [docs/auth.md](docs/auth.md) for the migration steps.

- `StandardRequest.Authenticate` reads `Authorization: Bearer <token>` and the `WithCookie` cookie, nothing else, and `AuthenticatedRequest` is `{Token, FromCookie}`: `APIKey` and `APISecret` are gone. The legacy `API-KEY` and `API-SECRET` pair is read by the separate `StandardRequest.LegacyCredentials(keyHeader, secretHeader)`, which applications compose after `Authenticate` on `ez.ENOTAUTHENTICATED` during their migration and delete afterwards.
- A request with no credentials is `ez.ENOTAUTHENTICATED` (401), not `ez.EINVALID` (400). A malformed `Authorization` header is `ez.EINVALID` and never falls back to the cookie.
- Cookie authentication (`requests.WithCookie`) needs `requests.WithMethod` on `requests.New`. Without it every method is treated as unsafe and needs an allowed `Origin`.
- `mcp.Config.Auth` defaults to `mcp.BearerPassthrough()` instead of `mcp.BearerToHeaders("API-KEY", "API-SECRET")`. Set it explicitly to keep the old mapping. The MCP server parses the header more strictly: a malformed `Authorization` header counts as no token.
- `oauth.Config.TokenPrefix` is required, 2 to 10 characters from `[a-z0-9]`.
- `oauth.Grant.Headers` is removed. `Grant` is `{Subject, Scope}`. `Scope` is stored exactly as the application set it, empty included; the client-requested scope is never granted and only echoes in the token response. `oauth.Pending.Scope` exposes the requested scope to `LoginURL` pages. A grant without `Subject` fails the login with `ez.EINTERNAL`.
- `oauth.Config.Fallback` is now `func(ctx context.Context, token string) (bool, error)`: `true` accepts the token, `false` rejects it with 401, and an error is reported to `OnError` and answered 500 instead of being taken for a bad credential.
- `oauth.Server.AuthFunc` returns the passthrough `Authorization: Bearer <token>` header instead of stored REST headers. The REST API resolves access tokens with the new `oauth.Server.Verify`.
- OAuth tokens are `<prefix>at_` and `<prefix>rt_` and are stored as SHA-256 hashes. Existing token rows are unreadable, so connected MCP clients reconnect once. There is no migration.
- Reusing a rotated OAuth refresh token, or presenting the same refresh token twice concurrently, revokes its token family. A client whose rotation committed but whose response was lost retries with a rotated token and must re-authorize; a failure before the commit is retried with the same token.
- `oauth.Store` gains `Swap(ctx, kind, id, old, value, expiresAt)`, a conditional replace that fails with `ez.ENOTFOUND` unless the stored value equals `old`. Custom stores must implement it; the bun and memory stores do, with no schema change. The Store must give read-your-writes across instances.
- `oauth.New` rejects negative durations and a negative `MaxLoginAttempts`, which used to take the default. The new `oauth.Never` is accepted only by `RefreshTokenTTL`; `IdleTTL` rejects it.

### Highlights

- **`components/auth/token`**: prefixed opaque bearer tokens (`<prefix>_` plus 43 base62 characters, 256 bits), stored as SHA-256 hashes, with `Generate`, `Hash`, `Prefix`, `Check`, `Hint` and `Equal`.
- **`components/auth/session`**: rotating session tokens for first-party apps, by cookie or `Authorization` header. Idle and max expiry, `Manager.Sweep` to delete expired sessions on a ticker (`Store.DeleteExpired`, with `expires_at` and `last_used_at` indexes from `CreateTable`), rotation with a grace period that waits for the previous token's grace to end, reuse detection (the previous token presented after its grace deletes the session, so a rotation response lost on the wire costs a login and a stolen previous token cannot take the session over), `LastUsedAt` writes coalesced by `TouchEvery` (which must be shorter than a finite `IdleTTL`), an optimistic lock on a `revision` column so concurrent requests re-read and re-decide instead of overwriting each other, with `Store.DeleteRevision` making the expiry and reuse deletes one conditional statement, a cookie `MaxAge` that follows `MaxTTL` so sessions without rotation stay logged in, a bun store for PostgreSQL and SQLite, and a memory store.

A rotated refresh row keeps the expiry it was issued with and is detected as reuse until then; under `RefreshTokenTTL` `Never` every rotation moves the family to `IdleTTL` from then, so no row outlives the connection and `Sweep` removes them all.
