compose design proposal · components/mcp

MCP for compose projects — a proposal

Draft for discussion, 2026-10-20 · module discovery

Six tools, always. Modules come from OpenAPI tags. Every call runs through the handlers REST already uses.

2The problem: one tool per endpoint does not scale

First bar extrapolated from Cloudflare's measured ~470 tokens per operation.

3Modules are OpenAPI tags

One tag becomes one module. The agent meets the same name in five places.

Where explain_term gets its text

Fields and the reverse index are free. Words only where the schema has none.

5The instructions the agent reads first

Returned by server/discover, built from tag descriptions. No list_modules tool.

server/discover → instructions Emma manages residential complexes: units, residents, dues, packages, visitors.
Modules (pass one to search_functions):
complexes complexes, buildings, contacts
units units, owners, occupancy
residents residents, invites, app access
packages parcels at the front desk
visitors visitor passes, guest log
meters water, gas, power readings
services utility contracts, consumption
payments dues, invoices, balances
access gates, tags, access log
incidents maintenance reports
notices announcements, polls
amenities bookings and rules
staff staff, shifts
devices intercoms, cameras, gates
reports monthly and financial reports
settings complex settings, charge categories
1. search_functions, then describe_function before the first call. Names are module.function.
2. explain_term for any concept you are unsure about. Spanish terms work.
3. whoami for complex_id. No session: pass it every time.
4. Destructive: fetch, summarize, wait for a yes, then call.
Money is integer cents (MXN). Dates YYYY-MM-DD.

7Rejected: a dynamic tool list

A tool that lists other tools cannot add them to the agent's tool list.

8Request path

Sandboxing is not authorization. Every api.* call is checked exactly like an HTTP request.

The run_script sandbox. Each script runs in a fresh QuickJS runtime compiled to WebAssembly and executed by wazero in the same process; the guest cannot read or write Go memory. Linear memory is capped at 64 MiB by the embedded binary, so allocation bombs end in an out-of-memory error, and the deadline is checked inside the compiled code, so JSON.stringify, regexes and array scans stop at the timeout too. Deep recursion throws a catchable RangeError (a few thousand nested calls fit); the 1 MiB runtime stack sits at the bottom of linear memory, so native code that overflows it traps instead of corrupting the guest or crashing the process. The binary is compose's own: about 270 lines of C (components/mcp/quickjs/sandbox.c) link the quickjs-ng engine without its standard library behind one export and two imports, and the Go side drives wazero directly, so there are no modules, files, timers or sleep, no network or environment, and stdout and stderr are discarded. A fresh instance per run is closed on every path, so timed-out and trapped runs hold nothing. The only way out is two host functions where Go enforces the catalog, the read-only rule, the call budget and the size caps on arguments (1 MiB), responses (4 MiB, a catchable Error), the result (1 MiB) and console.log (200 lines, 64 KiB); credentials never enter the guest. MaxConcurrent (default 4) bounds scripts across callers and each caller runs one at a time (refusals are ERESOURCEEXHAUSTED), so scripts hold about MaxConcurrent × 64 MiB plus overhead; the wasm ceiling does not bound the rest of the process.

Honest limit. This closes the availability holes of an interpreter on the Go stack (fatal recursion, builtins the timeout cannot stop, no heap limit), but it is an in-process sandbox, not a process boundary: a bug in wazero's compiler would be the way out, and a script can pin one core for the length of the timeout. WhoAmI gating stays required and Allow stays recommended for untrusted callers.

10How emma declares it shape, not final API

func MountMCP(e *echo.Echo, registry *api.Registry, pkgs *packages.Service) error {
	server, err := mcp.New(registry, mcp.Config{
		Name:         "emma",
		Instructions: emmaIdentity,
		Modules:      mcp.FromTags,
		Script:       mcp.ScriptConfig{Enabled: true, Timeout: 5 * time.Second},
		Composites: []mcp.Function{
			{
				Module:      "packages",
				Name:        "register_package",
				Description: registerPackageDoc,
				BackedBy:    []string{"ListUnits", "CreatePackage", "NotifyUnitResidents"},
				Handler:     mcp.Handle(registerPackage(pkgs)),
			},
		},
		Concepts: map[string]mcp.Concept{
			"debtor": {Text: "A unit whose balance is past its due date.", Aliases: []string{"deudor", "moroso"}},
		},
	})
	if err != nil {
		return ez.Wrap(err)
	}

	e.POST("/mcp", echo.WrapHandler(server.Handler()))
	return nil
}

func registerPackage(pkgs *packages.Service) func(context.Context, RegisterPackageInput) (RegisterPackageOutput, error) {
	return func(ctx context.Context, in RegisterPackageInput) (RegisterPackageOutput, error) {
		pkg, err := pkgs.RegisterAndNotify(ctx, in.ComplexID, in.Unit, in.Carrier, in.Note)
		if err != nil {
			return RegisterPackageOutput{}, ez.Wrap(err)
		}

		return RegisterPackageOutput{PackageID: pkg.ID, PickupCode: pkg.PickupCode}, nil
	}
}

The backend keeps its users and credentials; compose keeps the protocol. Each backend supplies three things: a Store (one table, bun-backed), a Login (how the user proves who they are: emma sends a code and verifies it, auditor3 checks an API key and secret) and, from Verify, the Grant: the REST headers the MCP server sends on that user's behalf. Both kinds of client work side by side: a token the store does not know falls back to the key:secret mapping when Fallback is set.
